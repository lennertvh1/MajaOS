# MajaOS

A simple management system for a home server in the style of ZimaOS/HexOS. It runs as root (systemd service) on **Debian 13** and manages **ZFS**, **KVM/libvirt** and **Docker** directly, plus optionally **Ollama**. Unraid is no longer used.

## The owner's situation

- New home server "Freddy": Ryzen 7 5700X + B550/X570 with ECC, 32 GB DDR4 ECC UDIMM, RTX 3060 Ti (8 GB), 2.5G network (10G later).
- Disks: 4× 2 TB HDD and 2× 512 GB SSD (intended as raidz1 pool `tank` and a mirror for apps and VMs; the docs and demo call it `fast`).
- About 20 Docker containers (Compose) and one VM with **Home Assistant OS**. Ollama runs as a container with the GPU.
- The owner develops on **macOS** in VS Code and speaks **Dutch (Flemish)**: talk to the owner in Dutch. The project itself (code, comments, docs, release notes, commit messages) is in English.

## Architecture

- `server.js`: Node 18.11+, **no dependencies** (built-in modules only). Serves `public/`, a JSON API under `/api/*`, auth and the Ollama proxy. Without an account and without `APP_PASSWORD` it is in **setup** (`needsSetup()`): all endpoints return 401 except `/api/config` and `/api/setup` (first account, only while there is none, with an origin check). `passwordEnabled()` = `APP_PASSWORD` or an own password. After starting it runs `vms.bootAutostart()` and `paths.detect()`. Ollama unreachable (ECONNREFUSED, 4 s time-out) → 503 with `notRunning: true` (`ollamaDown`); `e.data` of an error goes along in the JSON response.
- `lib/system.js`: `details()` for the System window (`systemWindow` in app.js: a click on the System widget, which is a `data-open="system"` button; refreshes every 2 s): per thread (`parseCpuCores`, the difference since the last reading) with its clock (cpufreq or /proc/cpuinfo), the CPU's temperature (hwmon k10temp/coretemp/zenpower), load, memory split up (apps, ZFS cache, other cache, free, swap), the GPU and bytes per second per card (`parseNetDev`, not lo/docker/veth/bridges of VMs). `run()` (execFile without a shell, `LC_ALL=C`, error message from stderr; gives up 5 s after its time-out even when the process doesn't exit, e.g. stuck on a dead disk), CPU/RAM from `/proc` (the ZFS ARC doesn't count as used), uptime, OS name, `nvidia-smi`.
- `lib/docker.js`: Docker API via `/var/run/docker.sock`. Own settings per app (WebUI address with `[IP]`/`[PORT:n]`, icon) in `DATA_DIR/apps.json` by container name, so they survive a restart or update. The console runs each command separately via `docker exec … sh -c EXEC_SCRIPT` and returns the folder after `\n\x01`. Logs are demultiplexed. Start/restart (`appAction`) then watches the container for 4 s (`checkStarted`): Docker says "started" also when the app quits a moment later, so a stop (or a restart loop) gives a 502 with `data {stopped, exitCode, last}` (`startError`: Docker's error, else the last line that looks like an error); the browser shows `last` untranslated with a *Logs* button on the message. *Update* = `docker compose pull` + `up -d` based on the compose labels (`updateTarget`), run as a job by `appstore.startUpdate` with the same progress and log as installing; afterwards `afterUpdate` checks that image again. The latest update job per app (by container name, kept an hour) is in `/api/apps` as `updateJob`. In the browser: a bar on the tile (`progHtml`, class `updating`, instead of the pulse of other actions), one poller for all running updates (`watchUpdates`), and the log in a window (`updateLogWindow`: click the tile while it updates, or *Update progress / Update log* in the menu). Own labels: `majaos.icon`, `majaos.webui`. *Rename…* in the app menu (and *Name* in its settings) stores a display name as `label` in `DATA_DIR/apps.json` (`/api/apps` `label`; `prettyName` in app.js uses it, `autoName` makes one from the container name); the container keeps its name. `ask(text, yes, check, {value, placeholder, label, max})` has a text field and returns `{value}`. Updates: `checkUpdates` compares the digests of the local image (`RepoDigests`) with the digest of the tag in the registry (`lib/registry.js`, HEAD on `/v2/<repo>/manifests/<tag>`, anonymous token via WWW-Authenticate). Result per image ref in `DATA_DIR/updates.json`; 2 min after start and every 6 hours, or right away via `/api/apps/check-updates`. After Update that image is checked again.
- `lib/xml.js`: small XML reader/writer for libvirt XML. Keeps order, whitespace and comments (reading and writing unchanged = exactly the same); `append` indents new elements neatly.
- `lib/vmhw.js`: hardware of a VM in the domain XML. `parseHardware` (nics, disks, cdroms, boot, hostdevs as `usb:vvvv:pppp`/`pci:0000:0a:00.0`, cpuPins), `applyHardware` (only what is in `change`: network cards by MAC, adding/detaching disks, cd-rom with possibly a new SATA drive, boot via `<boot order>` per device, hostdevs, `cputune/vcpupin`, clipboard channel `qemu-vdagent`, `firmware` uefi|bios (to BIOS: `<os firmware>`, loader, nvram and `<firmware>` go; to UEFI: through the Secure Boot path, off unless asked; VM off only, the old nvram file is removed), `tpm` (`<tpm model='tpm-crb'>` with the swtpm emulator, VM off only), `diskBus` (another bus for an existing disk: a new vdX/sdX name and its `<address>` dropped, VM off only), Secure Boot: `secureBoot` (null for BIOS) from `<os firmware='efi'><firmware><feature name='secure-boot'>` or the loader; switching drops `<loader>`/`<nvram>` so libvirt picks the firmware again, adds SMM when turning it on, and `saveSettings` (VM off only) removes the old nvram file in `/var/lib/libvirt/qemu/nvram`), `validateHardware` against the server's options. Cards of another type (e.g. `direct`) get `locked`. The server's devices: `lsusb` (without hubs), `/sys/bus/pci` + `lspci -Dmm` (IOMMU group, driver), CPU topology from `/sys/devices/system/cpu`.
- `lib/vmnet.js`: VM networks. libvirt networks (`net-list/net-dumpxml/net-info`, creating as NAT or isolated with DHCP in the second half of the subnet, `net-define` + `net-autostart` + `net-start`) and the server's bridges. Deleting only if no VM uses it; the subnet must be private and may not overlap with the server (also docker0/virbr).
- `lib/websocket.js`: minimal WebSocket server (RFC 6455): `proxyToTcp` passes the console (noVNC) on to QEMU's VNC screen on 127.0.0.1, `acceptWebSocket` is a plain WebSocket (for the terminal). `server.js` does the upgrade on `/api/vms/:id/vnc` and `/api/terminal` with the same sign-in and origin check.
- `lib/terminal.js`: terminal on the server (root shell). `script -qfec "stty rows R cols C; exec bash -l" /dev/null` (util-linux) creates the pseudo-terminal; messages from the browser are JSON `{t:'d', d}` (keys) or `{t:'r', cols, rows}` (size → `stty -F /dev/pts/N`). Each connection asks for a one-time ticket (`/api/terminal/ticket`, 60 s), with the password if *Security* asks for it. Opening and closing are logged. In the browser: `public/terminal.html` + `terminal.js` with xterm.js from `public/vendor/xterm` (6.0.0 + addon-fit, unchanged, MIT), in the same window as the console (`openTerminal`) or separately.
- `public/console.html` + `public/console.js`: console (`console.html#<name>`) with noVNC from `public/vendor/novnc` (1.7.0, unchanged, MPL-2.0; only `core/` and `vendor/pako`). Opens in MajaOS as an iframe in `#conWin` (`openConsole`); *Start with console* (VM card, VM menu, the edit window's Screen tab when off: `start-console` in `VM_ACTS`/`vmCommand`) starts the VM and opens it right away; *Pop out* opens the same address with `window.open` as a popup and calls the parent's `TB_closeConsole`. Ctrl+Alt+Del, typing text, fit/real size, full screen. **Paste**: Cmd/Ctrl+V is held back from noVNC in the capture phase, focus briefly goes to an invisible text box (`#cPasteSink`) so the paste event arrives in every browser, and the text is typed letter by letter as keysyms (+ `clipboardPasteFrom`). **Copying from the VM**: noVNC's `clipboard` event (needs `qemu-vdagent` + spice-vdagent in the guest) → `navigator.clipboard` when allowed (https), otherwise a button with `execCommand('copy')`. A simulated screen in the demo.
- `lib/vms.js`: libvirt via `virsh -c qemu:///system`. List from `virsh domstats` (CPU% = delta `cpu.time` relative to the VM's own vCPUs, RAM from balloon statistics). IP addresses of running VMs with `virsh domifaddr --source agent|lease|arp` (the first that gives something, kept 30 s). Editing = changing the domain XML (`editDomainXml` + `vmhw.applyHardware`) + `virsh define` (with `--security-info`, otherwise the VNC password disappears). New disks with `qemu-img create` in `VM_DIR/<name>/`, enlarging with `qemu-img resize` (off) or `virsh blockresize` (on); swapping an ISO also works live on a running VM (`change-media`). With pinned cores the number of vCPUs follows from the cores. Creating with `virt-install` (host-passthrough, VNC with a password; UEFI gets Secure Boot only for Windows (`uefiBoot`: `firmware.featureN` secure-boot/enrolled-keys), otherwise libvirt may pick the firmware with Microsoft's keys and unsigned systems like Home Assistant OS find no boot device): `vmHardware(body)` turns the chosen operating system (`OS`: Linux distributions, Home Assistant OS, TrueNAS, OPNsense/pfSense, FreeBSD, Windows 11/10/Server, other) into osinfo, firmware (UEFI or BIOS), disk bus, network card and TPM, with the family's defaults (`FAMILY`: Windows and unknown systems get SATA + e1000e) and the user's choices under *Advanced*; an osinfo name the osinfo-db doesn't know is retried once with the family's. From an existing disk the firmware defaults to `auto` (*Automatic (from the disk)* under Advanced): `diskFirmware` reads the first MiB with `qemu-img dd` and `parseBootSectors` looks for an EFI system partition (GPT type C12A7328-…, also 4096-byte sectors, or MBR type 0xEF): BIOS when the disk has partitions but none of them is one (otherwise UEFI only shows its shell, e.g. Kali's qcow2), UEFI when it has one or when there is nothing to read; the answer has `firmware` and `firmwareDetected`. `VM_OS` in app.js has the same ids (test/vmcreate.test.js checks that). Deleting = `undefine --nvram`; disks are only erased inside `VM_DIR`. Automatic start + delay is in `DATA_DIR/vms.json`; libvirt's autostart is then turned off. A marker in `/run/majaos` prevents starting twice.
- `lib/vmmedia.js`: files for VMs (ISOs and disk files .qcow2/.img/.raw/.vmdk/.vhdx/.vdi) in the New VM form (`vmCreateWindow`: *Upload…*, *From a link…*, *Choose on the server…*, and for an existing disk *Use the file as it is (no copy)*). `upload` (PUT, the body is the file, written through `files.receive` into the ISO folder) and `download` (Node's fetch, redirects followed, the name from Content-Disposition or the final address (`fileNameFrom`), progress from Content-Length) refuse a name that exists and check first that the unpacker is there (`needTool`: `xz-utils`, `unzip`, both in install.sh/upgrade.sh); a packed file (.xz, .gz (Node's zlib), .zip: the largest disk file inside, `pickZipMember`) is unpacked next to it in a job and the archive removed (also when unpacking fails). Jobs in memory (`/api/vm-media/jobs/:id`, Stop = DELETE), percent from `xz --robot --list` / `unzip -l` (`parseXzList`, `parseUnzipList`). Temporary files are hidden (`.vm-…` + `.majaos-upload`, opened with `wx`). `browse` lists folders and disk files/ISOs on the pools only (no hidden entries, real paths), `checkSource` accepts a full path only when it is a plain file (no symlink) of the right kind on a pool. `createVm` takes such a path as `source`; `inPlace: true` (only qcow2 or raw per `qemu-img info`) makes that file the VM's disk without a copy or a folder in VM_DIR, and is refused for a file another VM uses (`usedFiles`: every VM's disks with their backing chain; a copy of the disk of a running VM is refused too). `vmOptions` marks those images with `usedBy`. Deleting the VM keeps a file outside VM_DIR. Node's `requestTimeout` is off (`tune` in server.js): uploads of large files took longer than its 5 minutes.
- `lib/paths.js`: where folders go: `appdata`, `vms`, `isos`, `shares` in `DATA_DIR/paths.json`, falling back to the old variables `APPDATA_DIR`, `VM_DIR`, `ISO_DIR`, `SHARES_DIR`, otherwise `null` (`shown()` then gives `/<pool>/…` to display; installing refuses with a message). `createDefaultFolders` creates the datasets appdata, media, backups, vms, isos on a new pool (appdata/media/backups owned by `APP_UID:APP_GID`); `adoptPool` puts whatever had no (existing) place yet on that pool (shares = the pool itself); `detect` (at startup, in Settings → Storage and in the app store as soon as the folder is missing: `ensureAppdata`) looks for an existing folder (`pickFolder`) for whatever isn't set or no longer exists: for appdata first where the containers have their bind mounts (`appdataFromMounts`: …/appdata/<app>), then a dataset with that name (also deeper), then a plain folder `<pool>/appdata`. In Settings → Storage you can also point to an existing folder yourself (*Existing folder…*, `migrate.usePath`: nothing moves). The app store and `vms.js` read the folders every time (`APPDATA_DIR()`, `VM_DIR()` are functions).
- `lib/migrate.js`: Settings > Storage (`storagePane` in app.js). `overview` (paths, pools via `zfs list -d0`, apps with a bind mount in the app data: per compose project, and `manual` without compose or with a compose file that isn't on the server, as with Portainer; `groupContainers`), `setLocation` (vms/isos/shares on a pool, creating the dataset if missing, files don't move along) and `migrateAppdata`: one job in memory (steps prepare → stop → copy → compose → start → done): dataset `<pool>/appdata`, stop compose projects, `rsync -aHAX --numeric-ids --info=progress2` (percentage from the output), replace paths in the compose files (`replacePath`: full paths only, `.bak`), `paths.save`, `up -d --force-recreate` (or `--no-start` if the project wasn't running). If it fails before switching over, the apps start again with the old folder. The old folder always stays; folders with the same name in the target folder → 409. **A second pool:** `homeFolders` says where the default folders are (app data, ISOs, VM disks, new shared folders, and the media and backups datasets); `createPool` (and `lib/mixed.js`) then doesn't make them again, unless `folders: true`. Instead the pool form offers to move them (`move: [kinds]`): `checkMove` refuses backups (devices and Kopia use them), VM disks while a VM runs or has snapshots, and a move that is already running, before any disk is erased; after the pool is made `migrateFolders` runs one job like the app data move (datasets, stop the apps that use any of the folders, rsync each, compose files, `shares.movePaths` for shared folders inside, the VMs' domain XML for ISOs and disks via `virsh define`, `paths.save`, start the apps; `items` in the status). The old folders stay.
- `lib/appstore.js`: catalogue from the Unraid Community Apps feed (`applicationFeed.json`, cached 24 h in `DATA_DIR/appstore.json`). `normalizeFeed` removes plugins/deprecated/blacklist, cleans up BBCode (`cleanText`; for the description with `md`: bold, headings, links and `[*]` become Markdown, lines are unindented; `summary` = `plainText`) and computes popularity (one template per image, the name must fit the image) and `featured`. `prepareFields` translates Unraid paths (`PATH_MAP`), 99:100 → `APP_UID:APP_GID`, `TZ`, and fills an empty `/config` with `APPDATA_DIR/<name>` (`auto: true`). `buildCompose` creates `compose.yaml` (own YAML writer: strings as JSON) with labels `majaos.store`, `majaos.data`, `majaos.icon`, `majaos.webui`. **GPU:** the NVIDIA device request goes in when the template asks for it (`--runtime=nvidia`/`--gpus`) or, if Docker has the nvidia runtime (`sys.dockerNvidia()`, option `nvidia`), for Ollama (`GPU_IMAGES`) and templates with `NVIDIA_VISIBLE_DEVICES` (`wantsGpu`); without the runtime a template's GPU request is left out with a warning, because Docker would refuse to start the app. `iconFor` gives apps without a `majaos.icon` label an icon: first from the catalogue (same image), otherwise from dashboard-icons by name (checked once, remembered in `DATA_DIR/icons.json`). Before every install (app store, own app, compose file) `makeBindFolders` makes the bind folders that don't exist yet and gives each folder it made to `APP_UID:APP_GID` (one level at a time, `lchown`), also outside the app data (e.g. `/tank/media/movies`), because Docker would make them as root; only inside the app data, `STACKS_DIR` or a pool's datasets (`bindFolderPlan`, also through symlinks), never an existing folder. Installing = a job (`startJob`) that runs `docker compose pull` + `up -d` in `STACKS_DIR/<name>`, and cleans up on an error. A pull (install and update, `PULL_LIMITS`) is only stopped after 10 minutes without output (`runStream` `idle`) or after 4 hours: large images like Ollama took longer than the old 15 minutes. `jobLog` updates the output of `--progress plain` like a terminal: one line per layer, container or network, updated in place; `jobProgress` derives the percentage from it (downloading 3–85 %, starting 85–99 %). In the browser: `jobHtml`/`drawJob` (bar, step, *Details* with the output, opened on an error). **Own app**: `normalizeImage` turns a name, `docker pull …` or a link (Docker Hub, GitHub package, Quay) into an image; `inspectImage` reads with `registry.imageConfig` (manifest → right architecture → config blob, without downloading) the ports (EXPOSE), folders (VOLUME) and proposes PUID/PGID/TZ, a free port, folders in `APPDATA_DIR/<name>`, a WebUI address and an icon; `installCustom` builds the compose file (`buildCustomCompose`, label `majaos.custom=1`) and uses the same job. In the browser the form reuses `composeFormMount`. The own-app window first asks *An image* or *A Docker Compose file* (`data-csrc`); the second is `composeAppForm`: name (suggested from `container_name` or the first service), the file (pasted or *Open a file…*), an optional `.env`, straight to `installCompose`. **Advanced** (app store) and *Fields/Code* (own app): `draft` creates a draft (`{store, …}` like installing, `{custom}`, `{text}` or `{text, form}`), reads it with `composeform.loadProject` and returns `{text, form, formError, dockerNetworks}`, so fields and code are always the same file via the server (unknown keys stay). `installCompose({name, text, env})` (no MajaOS labels: `listApps` still counts it as an own app (`custom`) because its compose project lives in `STACKS_DIR/<project>` (`inStacks`), and its data folders are its bind mounts inside that folder or the app data (`dataDirsOf`); removing it removes the whole stack, and without "also delete the data" the data folders inside the stack folder stay; a pasted service block without `services:` above it gets it first: `composeForm.wrapServices`, answered as `wrapped`; compose errors through `composeError`, which says plainly when a service is at the top level) writes exactly that text to `STACKS_DIR/<name>/compose.yaml` (and `env`, if any, to `.env` next to it, 0600), checks it with `docker compose config`, creates missing bind folders (owned by `APP_UID:APP_GID`) and starts the same job. *Data folder* (`__datadir`, suggestions from `folders` = mount points of the datasets): all paths below it move along (`rebasePath` in app.js). In the browser: `advancedEditor`, `dataDirHtml`, `advToggleHtml`. **Simple install:** the app store window has an *Advanced* switch in its title bar (`#winAdv`, `winAdvSwitch()`; `openWindow` hides it again; on by default for the experience level expert). Off: only what has no default (`needed` in `storeWindow`: required fields with an empty value, e.g. a database host) and the folders with the user's own files (`storeUserFolder`: a Path that isn't auto, not in the app data and not a system path like docker.sock or /dev; folder fields suggest the datasets via `list="appFolders"`, and while typing also the folders inside the folder typed so far (`suggestDirs` in app.js, `GET /api/folders?path=` = `appstore.folderSuggestions`, pools only through `vmmedia.browse`; also for the compose form's volumes (`dirSuggest`), shared folders and backups)), in `[data-ask]`, plus one line on what to do (`.store-todo`) and a summary (`data-install-note`), all `[data-simple]`. On (`setFull`): everything in `[data-full]` (name, data folder, *Edit the compose file* = `__adv`, network, ports, all fields, *More settings* open). Turning it off while the compose editor is open asks first (`leaveEditor`). A required field that is empty inside `[data-full]` turns it on. The own-app form still uses *Customize* (`details[data-custom]`). The description above the form: `storeOverview` (bullets → lists, a short line on its own → heading, then `mdToHtml`) gives a summary (the first paragraph, at most a few sentences) and the rest folded under *More about this app* (`.store-about`); *Requires* and the warnings are one card *Before you install* (`.store-notes`). The overview is translated per paragraph (`tr`). The cached catalogue has a `format` (`CACHE_FORMAT`): bump it when `normalizeFeed` changes, so servers fetch it again. The default network is `host` (`networkDefault`, also the server-side fallback when `network` is missing; the template's own network is ignored) and the data folder is `APPDATA_DIR/<name>`. **WebUI on host:** the app listens on its own port, so a port that still has the template's value is not a change (`defaults` in `buildCompose`); a template without a WebUI address gets one from its web port (`WEB_PORTS`, or the only TCP port); the ports the app listens on go in the label `majaos.listen` (read back as `hostPorts` in `/api/apps`), and `hostClashes` checks them against published ports, other host apps and MajaOS itself (`listenPort()`, 80 by default). On a clash `details()` / `inspectImage` return `networkDefault: 'bridge'` instead (Docker then publishes the template's port); choosing host anyway is refused with a 409. Network: when installing the user can choose `network` + `ip` under Customize, and can add `extraPorts`. Port fields are always editable. With host or an own address (macvlan/ipvlan) Docker can't remap ports: a changed template port goes to the app's own port setting (a Variable with "port" in its name and the same value, e.g. WEBUI_PORT) and `majaos.webui` follows (`[PORT:n]`); without such a setting there is a warning. Only *+ Port* (extra ports) switches the browser to the default network. Every template field that isn't required has a × (`data-field-del`): hidden and disabled, listed under the fields as *Left out* with ↺ to put it back, and sent as `removed` (also to the draft), so `storeCompose` leaves it out. A fixed IP on the default network: `dockernet.networkFor`/`formNetwork` put the app in the shared bridge network **maja** (`ensureMajaNetwork`: the first free of 172.30.0.0/16, 172.29.0.0/16, 10.250.0.0/16, label majaos=1; `checkFreeIp`: in the subnet, not the network/broadcast/gateway address, not used by another app); refused for a compose file with several services, which would be cut off from each other. **Own address in my home network** (choice `@lan`, `LAN_CHOICE`): `ensureLanNetwork` uses an existing macvlan/ipvlan on the home network's card, or creates macvlan `lan` itself (card with the default route, its subnet, the router as gateway, IP range = the top /27 via `lanRange`); **Addresses for apps** (Settings → Docker networks, `#lanRangeForm`): a range from … to … the user chooses (any addresses in the home subnet, e.g. outside the router's DHCP pool) in `DATA_DIR/lan-range.json`, `POST /api/docker-networks/lan-range`; without one `appRange` falls back to the network's IP range (or the top /27) without the broadcast. `lanInfo` (`GET /api/docker-networks/lan`) returns it as `range` and suggests a free address (`suggestLanIp`: in that range, not used by an app, a shim or the server, not in `ip neigh`, no answer to a ping). `networkFor`/`formNetwork` (also for the home network's own-address network chosen by name) go through `lanAddress`: a typed address must be free and never the server's address (`checkLanIp`); outside the range is allowed, the browser's IP field then warns while typing (`paintIpField`), and a new app without an address gets the suggestion (an edited app keeps what Docker gave it). In the browser the IP field switches to *Fixed address* with the suggestion filled in (`paintIpField(…, onFill)`) as soon as an own address in the home network is chosen, unless the user picked a mode or typed an address (`ipChosen`; the compose form only after its network changed). The shim's default address is the top of that range (`n.appRange`). In the browser the IP field (install form and compose form, `ipFieldHtml`/`paintIpField`) is a choice *Automatic* (empty: Docker picks a free address, for an own address from the lan network's range; Docker can't use the router's DHCP) or *Fixed address* (required then; `ipFixed`, not enumerable, for `composeFormCheck`), with an example in the right subnet as placeholder (`lanInfo` suggestion, the maja subnet or the network's own). With *Host* the app has the server's address, so there is no IP field and the help points to the own-address choice. With macvlan/ipvlan (own address) there are no ports on the server and `webui()` in `lib/docker.js` fills in the own address for `[IP]` and the app's port for `[PORT:n]`. On host also the app's port; on bridge the published port (TCP first), and if `[PORT:n]` isn't mapped anywhere, the only published TCP port. If the container list gives no ports, they come from inspect (`portsOf`).
- `lib/layout.js`: layout of the home screen in `DATA_DIR/layout.json`: `{items: ["<container name>" | {folder, name, apps: [...]} | {heading, name} | {spacer}]}`. **Sections and empty spots** (like Home Assistant's sections): a heading (`headingTile`, id `h…`) is a title over the whole width that starts a section; *New heading…* in the dashboard's menu puts it after the tile before the spot that was clicked (`insertIndexAt`), its ⋯ or a right click renames or removes it (`headingCommand`; the apps stay). A spacer (`spacerTile`, id `g…`) is an empty cell, dashed only while dragging; dropping a tile on an empty cell (also the empty cells after the last apps, which show while dragging) fills the cells before it with spacers and leaves a spacer where an app was, so the rest doesn't move (`cellAt`/`placeAtCell`, undone by `clearTemp` while the pointer moves on); a spacer under the pointer is taken by the tile; a right click on one gives *Remove empty spot*. Spacers that end a section are dropped (`trimSpacers`, also in app.js). The home grid is always the cell grid (`home-mix`, `grid-auto-flow: row`, no `dense`, so the order is the reading order); its columns follow the grid's own width (`fitHomeCols`: resize and a ResizeObserver), never during a drag, and `html` has `scrollbar-gutter: stable` (a scrollbar appearing while dragging moved every tile and the page). `validateLayout` allows each app only once, turns a folder with one app back into a plain app and drops empty folders. In the browser: `homeItems()` (new apps at the end, apps that are gone removed), dragging with pointer events whenever the grid is showing (a click that does not move still opens; middle of an app = make a folder, edge = before/after, dragging out of the folder panel = out of the folder; holding a widget shows the cell grid), folder panel `#folderPanel` (name, Ungroup) and in the menu *To folder…* / *Out of folder*. A folder tile has its own menu (⋯ or a right click, `openFolderMenu`/`folderCommand`, `menu.dataset.forFolder`): each app in it with an update gets *Update <name>* (or its update progress), *Update all in this folder* when there are several, then open, rename and remove the folder. App names wrap onto two lines (`.app-name` line clamp) instead of being cut off. - `lib/macvlanshim.js`: the shim (Settings → Docker networks, a switch on each macvlan/ipvlan network: *The server and its other apps can reach these apps*). Linux never delivers traffic between a macvlan/ipvlan child and its parent card, so the server, host-network apps and apps behind Docker's NAT couldn't reach apps with their own address. With the shim on, the server gets its own macvlan (or ipvlan l2) link on the network's parent (`ifName`: `mshim<8 hex>`, a stable MAC from the network name and machine-id, `macFor`) with one address (`/32`; `defaultAddress` = the top of the IP range, never the broadcast, gateway or an app; the user can change it when turning it on, or tick *Use the server's own address* = `{server: true}`, resolved each time by `serverAddress` from the parent card (or another card in the subnet); no address is used up, but other devices may see two MACs for it) and routes through it: the IP range plus a `/32` for each app outside it (`wantedRoutes`; never the whole subnet, that would cut the server off from the home network). `DATA_DIR/shims.json` {networks {name: {address} | {server: true}}}; `tick` (at start and every 30 s) makes the links again after a restart or a network reload and keeps the routes in step with the apps; a removed Docker network drops its shim. `info` also gives the shim's `mac` (macvlan: `macFor`, fixed per network and server; ipvlan: the parent card's), shown next to its address so it can get a reservation in the router. - `lib/network.js`: view the network (`ip -j -d addr`, `ip -j route`) and change it via ifupdown (`/etc/network/interfaces`): card, DHCP or static address, gateway, DNS, bridge `br0`. Changing a card only rewrites that card, and the bridge only when the card goes into it or was its port (`bridgePorts`): changing a second card must never drop br0 of the first. A card on its own gets `allow-hotplug` (unless the file had it as `auto` or it was br0's port). The DNS servers written are those of the whole file (`fileDns`), so another card's own servers stay. Applying makes a backup copy in `DATA_DIR/network-previous`, and the new file is only written inside `reload(ifaces, next, onWrite)`, after `ifdown` with the old file (ifdown reads the current file to know how to take a card down: written first, a DHCP card going into br0 was "manual" already and kept its DHCP client, which put an address and route on the bridge port and made the server unreachable), `stopDhcp` (dhclient -x, dhcpcd -x) and a flush; after `ifup`, `clearPorts` removes any address left on a bridge port or bond slave (`portsIn`); rollback goes the same way back. **Leftovers in the kernel** (`strayPlan`/`clearStray`, in `reload` after writing and in every `watchCards` tick): br0 or bond0 that the file (with what it sources from interfaces.d, `withSourced`) no longer has is deleted, and a card the file gives its own stanza but that still sits in a bridge or bond the file doesn't put it in gets `nomaster`; those cards then go down (with their DHCP client) and the tick brings them up again. Otherwise a bridge removed while ifdown no longer knew it kept the card as its port, and the card never got an address. It reloads only the changed card (and the bridge with its ports if it is involved): `ifdown`, then `ifup` for each auto/allow-hotplug name of the file (`upNames`) that has a cable (`hasCable`; without one DHCP would wait a minute; watchCards brings it up later), and the check afterwards is skipped for a card without a cable and wants a default route only where there was one and puts everything back after 2 minutes without confirmation, or right away when the reload fails or the card/bridge gets no address and route within 45 s (`reachable`). A bridge keeps the card's MAC (`bridgeLines`: `bridge_hw` + `hwaddress ether`): otherwise udev gives br0 its own MAC and DHCP another address (or a reservation by MAC doesn't apply); at start `fixBridgeMacs` adds it to a one-card bridge written before (`addBridgeMacs`) and brings the bridge up again when its MAC is wrong. ifupdown never reacts to a cable, so `watchCards` (every 20 s, not while a change waits for confirmation) runs `ifup` for each auto/allow-hotplug card or bridge that `ifquery --state` doesn't list while it (or a bridge port) has carrier (`cardsToBringUp`); a link that is down gets `ip link set up` first, because the kernel only reports carrier on a link that is up. Other `iface` blocks stay unchanged. Needs the package `ifenslave` (install.sh, upgrade.sh; `canBond`). - `lib/fans.js`: Settings → *Cooling* (`#settings/cooling`, `coolingPane` in app.js). Reads `/sys/class/hwmon` (`HWMON_DIR` for tests): temperatures (unused inputs left out; `drivetemp` gets its disk's name; the GPU from nvidia-smi as source `gpu`), fans (RPM) and PWM channels (fanN ↔ pwmN of the same chip). Ids stay the same after a restart: `<chip>@<device>/<file>`. Per channel `auto` (the chip/BIOS, as before), `fixed` (%) or `curve` (a temperature → %, straight lines between 2–8 points, `curvePercent`), with a minimum; `tick` every 3 s sets `pwmN_enable=1` and the value, and remembers the chip's own mode in `orig`. Safety (`target`): never below the minimum, 100% from 85 °C on a CPU sensor and when a curve's source is gone. When MajaOS stops (also a crash) systemd runs `node lib/fans.js --restore` (`ExecStopPost` in majaos.service): every controlled channel gets its `orig` back. *Look for sensors* (`probe`) loads `nct6775`, `it87`, `drivetemp` and lists them in `/etc/modules-load.d/majaos-fans.conf`. A folder without users and without guests is never written (an empty valid users = everyone). `apply` first checks with `testparm -s` on a copy, then writes, puts one include line in smb.conf and runs `smbcontrol smbd reload-config`. A new folder = `zfs create <pool>/<name>` with chown to the app user; an existing folder must be on a ZFS mount point. Users: `useradd --no-create-home --shell /usr/sbin/nologin` + `smbpasswd -a -s` (password via stdin, `run({input})`); deleting isn't possible if someone is the only one with access to a folder. In the browser: a window of its own (`sharesWindow`), via the *Shared folders* button at the top and from Storage. Every share in `/api/shares` (and the answer of saving) carries `writable` (can the app user write in the folder: `writableBy`), `owner` and `fixRefused`; a folder of root (e.g. an `isos` or `vms` dataset of an older pool) shows a warning with *Make writable* → `POST /api/shares/:name/fix-owner` (`fixOwner`: `find -xdev`, without `.zfs`, `chown -h` to APP_UID:APP_GID and `chmod u+rwX,g+rwX` on folders and files only). `fixRefusal` refuses a whole pool, the app data and the VM folder. Saving a share where a user or group may write does the same by itself (`writableOnShare`, a failure only logs: the warning then stays). New pools give `isos` to the app user too.
- `lib/backup.js`: Backups (`backupWindow` in app.js, *Backups* button at the top and the `backup` widget). Three tabs. **Devices** (`method` share or kopia; without `method` = share): with the backup app everything goes through `lib/kopia.js`; with a shared folder `createDevice` creates `<pool>/backups/<name>` (`zfs create -p`, optionally `quota=…G`, chown to the app user) and a shared folder with the same name via `shares.saveShare` (one user rw, Time Machine for `mac`); if the share fails, the dataset goes away again. Deleting removes the share, the dataset only with `?data=1` (`zfs destroy -r`, only `<pool>/backups/<name>`). `lastChange` = newest mtime up to two levels deep (max. 3000 items). **Connections** (rclone remotes) in `DATA_DIR/rclone.conf` (0600, own INI reader/writer `parseConf`/`buildConf`; passwords via `rclone obscure -` on stdin, never on the command line). Kinds in `PROVIDERS` (drive, onedrive, dropbox by signing in; s3, sftp, smb, webdav with fields); new = write + `rclone lsjson` as a test, otherwise removed again. Signing in: `startAuth` starts `rclone authorize <type> --auth-no-open-browser` (listens on 127.0.0.1:53682), fetches the local `/auth` link and gives the redirect (the sign-in page) to the browser; the user pastes the address Google/Microsoft/Dropbox sends back to, `finishAuth` forwards the query to 127.0.0.1:53682 and reads the token (`parseAuthToken`: JSON, or base64 of `{token, …}` in newer rclone). OneDrive gets `drive_id`/`drive_type` from Microsoft Graph (`/me/drive`). Pasting a token (from `rclone authorize` on a PC) and `reconnect` (sign in again, same name) also work. **Tasks** in `DATA_DIR/backup.json` {jobs, devices}: `direction` push\|pull, `mode` copy\|sync, `schedule` {every: manual\|hourly\|daily\|weekly, time, day}, `encrypt` (push only, only when creating: crypt remote `hb-crypt-<id>` around `remote:remotePath`, destination `…:files`, versions `…:versions`), `versions` + `keepDays` (`--backup-dir "<destination> (old versions)/<date>"`, then `rclone delete --min-age` + `rmdirs`), `excludes`, `bwlimit`. Tasks created before 0.6 have no `names: 'en'` and keep the Dutch folder names on the destination (`bestanden`, `versies`, `(oude versies)`; see `targets`): never rename those. `validateJob`: refuses sync/versions to the top folder of an unencrypted destination, pull never into a whole pool. `buildArgs` (`--use-json-log -v --stats 2s --links`), `parseLogLine`/`summarize` for progress and the log. Running tasks only in memory (`live`); `preflight` refuses if the dataset isn't mounted or the source folder of a sync is empty. After pull/restore `chown -R` to the app user. History (20) in the task, log (400 lines) in `DATA_DIR/backup-logs/<id>.json`. Schedule: `tick` every 30 s, `nextRun` in the server's time zone; missed times are caught up once; if the previous run is still going, that time is skipped. *Dry run* = `--dry-run`, *Restore* = `copy` from the destination to a folder on the NAS.

Files in `DATA_DIR/kopia` (repository.config, server.cert/.key, server.env with `KOPIA_PASSWORD` (0600, never on the command line), state.json {enabled, pool, dataset, path}). Each device = Kopia user `<name>@<name>` (lowercase; on the device you fill in that name as Override Username and Override Hostname). Password `newPassword()` (xxxxx-xxxxx-xxxxx-xxxxx, without l/1/o/0) via `server user add/set --user-password`; it is returned only once (`bk.secret` in app.js). A new device gets a code right away; *Pairing code* on a device creates a new one (the device then has to pair again). - `lib/vmsnap.js`: snapshots of VMs (tab *Snapshots* in the VM window, `drawSnaps`/`paintSnaps` in app.js; carried out right away, Save is hidden there). A snapshot manager like VMware's: the history as a tree (children oldest first; a snapshot whose parent is gone hangs at the top), *You are here* under the current snapshot, the chosen snapshot's details with *Go back to this snapshot* and *Remove*, *Take snapshot* (`vmEditWindow(id, 'snapshots', {snapNew: true})`) and *Back to the current snapshot*. Always external (`--diskspec <disk>,snapshot=external`, cd-roms `snapshot=no`): internal snapshots don't work with the raw nvram of UEFI VMs. If the VM runs, with memory (`--memspec file=<disk>.<name>.mem`), unless `diskOnly` or the VM has a passed-through device; shut off = `--disk-only`. List via `snapshot-list --topological` + `snapshot-dumpxml` (`parseSnapshotXml`), revert `snapshot-revert`, delete `snapshot-delete` (merges the overlay; libvirt 9.9+). For a VM that is off, libvirt starts a QEMU to merge, which couldn't open the root-owned base disk ("Permission denied"): `deleteOffline` merges with `qemu-img commit` itself when it is certainly safe (`offlinePlan`: no later snapshots, and per `qemu-img info` no other file builds on the overlay or, when merging, on the disk below), points the VM to the disk below (`virsh define`), removes the overlay and the `.mem` file and runs `snapshot-delete --metadata`; otherwise libvirt does it, and a "Permission denied" there asks to start the VM first (a running VM merges with blockcommit itself). `deleteVm` also erases the whole chain with the disks (`backingChain`, `qemu-img info --backing-chain`) and the `.mem` files.
- `lib/sysbackup.js`: backups of apps and VMs to a folder on the NAS (*Backups → Apps and VMs*, `bkSystem`/`sysJobForm`/`sysRestore` in app.js). Tasks in `DATA_DIR/sysbackup.json` {jobs [{id, name, dest, apps ['compose:<project>'\|'container:<name>'], vms, stopApps, vmMode live\|shutdown, keep, schedule, …}]}; schedule and `nextRun` from backup.js. Each run `<dest>/<YYYY-MM-DD_HHMMSS>/` with `manifest.json` (0600), `apps/<app>.tar.gz` and `vms/<vm>/` (domain.xml with `--security-info`, nvram, `<disk>.qcow2`). An app = a compose project (`parseUnits` on `/containers/json`): included are the compose files + `.env`, bind mounts inside the app data or the project's folder, and volumes; other bind mounts are listed in `skipped` (e.g. /tank/media, docker.sock). `stopApps` stops the running containers via the Docker API and starts them afterwards. One backup at a time; stopping kills tar/qemu-img or runs `domjobabort`. Restore: app = stop the containers, rename the current folders to `<folder>.before-restore-<date>`, unpack the tar, start; VM = must be off and without snapshots, disks moved aside and `qemu-img convert` to the old format, nvram back, `virsh define` if the VM no longer exists.

That screen asks for a language (en, nl, fr, de, es, pt, it, pl, zh, ja), then the network (per card: DHCP, a fixed address with an optional gateway and DNS, or not used; `installer.validateCards`: one gateway at most, DHCP or a gateway somewhere, errors carry `card`; `GET/POST /api/install/network` in `iso/serve.js`, applied to the live system right away with `ip`/`dhcpcd`, checked with a real connection to deb.debian.org:80, and written for the installed system with `installer.buildInstallInterfaces` (the home card (gateway, else the first DHCP card) in bridge `br0` with its MAC, so VMs are in the home network by default; other DHCP cards allow-hotplug) and `installResolv`, so the installed system uses ifupdown like Settings > Network; `installer.parseCards`, which ignores 169.254.x.x; the step asks the server every 1.5 s (`watchNetwork`, focus kept); for a card that got a cable but has no address and no dhcpcd of its own (`dhcpcdRunning`, which also recognises dhcpcd's renamed process title) the server starts `dhcpcd -4 --noipv4ll --noarp -b` once, before its internet check, and never stops a running dhcpcd; the live system's dhcpcd.conf has `nohook hostname`, `nodelay`, `noarp`, `noipv4ll` and `clientid` instead of `duid` (a DUID that is new at every start made a mesh router answer only after a minute); the installed system gets `nohook hostname` and `clientid` too), then the account (`POST /api/install/account`: `installer.validateAccount` = a user name the live system's /etc/passwd doesn't have and not reserved, a password like `auth.validateNewPassword` without control characters, typed twice; *Show the password* to check the keyboard; kept in memory by serve.js), then a disk, and refuses the stick it booted from. So the installed server never waits in setup: the account is the owner in MajaOS and the login of the server's own screen (with sudo). The network check before erasing is only fatal when internet is needed (debootstrap or NVIDIA); the network step lets you go on without internet after a warning. Only after *Erase and install*, `iso/run-install.sh` partitions that disk. **Image path** (the squashfs, found with `findmnt -t squashfs`, has `/opt/majaos/server.js`): `rsync -aHAX` of the live system to the disk (bar from `--info=progress2`), then cleaned (kiosk unit, the autologin root shells on tty2/ttyS0, the masks of getty@tty1 and plymouth-quit, the `majaos-live.conf` drop-ins, the installer's quick dhcpcd options) and made unique (machine-id, SSH host keys, `SESSION_SECRET`, `zgenhostid`, Samba's secrets.tdb), live-boot purged, its own initramfs, the GRUB package for UEFI or BIOS from the cache; no internet needed except for NVIDIA (install.sh `--nvidia` again, else firstboot). **Fallback** (no MajaOS in the squashfs): debootstrap + apt, then MajaOS itself: `install.sh` runs in a chroot on the new disk with `MAJAOS_CHROOT=1` (services are only enabled via `enable_now`/`disable_now`/`restart`, ZFS and NVIDIA are built with `dkms autoinstall -k` for the newest kernel in the chroot (`KVER`), the libvirt default network gets its autostart link, `/run` is an empty tmpfs so nothing starts), the bar follows the `==> ` steps of install.sh (`watch_majaos`, output in `/run/majaos-install/majaos.log`), and on success the address goes into `/etc/issue.d/majaos.issue` and `/opt/majaos-setup` is removed: MajaOS runs at the first boot without firstboot. The test workflow and the release workflow both pass `--live`. GitHub Actions (`.github/workflows/iso.yml`, "Release and ISO") creates the release for every pushed tag `v*` (title = first line of the tag message, text = the rest, in Markdown; a tag with a `-` becomes a pre-release), then builds the ISO and attaches it; a release you create yourself on github.com also gets an ISO. ## Working agreements

- **Everything in the project is English**: code, comments, test names, docs, release notes, commit messages and every text in the interface. Interface text: short, plain sentences, active verbs, error messages that say what is wrong and what you can do.
- **Multilingual (English + Dutch, more later)**: the English text is the key. Put every new text in `app.js` in `t('…')`, with values as `t('Removed: {name}', { name })` (never glue text together), and add the Dutch translation to `public/lang/nl.js` (Flemish: short, plain, "je"). Fixed text in `index.html` (also `placeholder`, `aria-label`, `title`) is translated by `collectStatic()`, but needs a translation too. Server messages are English: the browser translates them with `tr()`, so add a new message to `nl.js` too, as a template if it has values (e.g. `'Port {port} is already used by {app}. Choose another port.'`). Data from the server that is text (warnings, categories, lines of a job) goes through `tr()` when shown. A word with two meanings in another language gets a context: `t('Devices', null, 'backup')` looks up `"backup\u0004Devices"` first (in Dutch *Toestellen* for backups, *Apparaten* for USB/PCI). Never use `t` as the name of a variable or parameter. Apostrophes are fine in keys (escape them in single-quoted strings, also in test names).
- No npm dependencies without asking first. No build step. System packages go through `install.sh`.
- External commands always through `run()` with an argument list, never through a shell. Validate names and paths from the user (see `NAME` and the `ISO_DIR` list in `lib/vms.js`).
- A folder on the server that is shown somewhere (pools, datasets, Settings → Storage, shared folders, VM and ISO folders, backup folders) gets `dirLink(path)` in app.js: a folder button that closes the window or Settings and opens it in Files via `/api/files/locate` (`volumes.locate`). Only for folders that exist.
- Little text on screen: an explanation goes behind a **?** (`hint(text)` in app.js: a tooltip on hover, focus or tap; `paneHint(text)` puts it next to a settings pane's title), next to the title, field or checkbox it explains. What the user must see stays visible: status, warnings, errors, what happens next. A section is a card with a clear heading (`.section-head`, `.pool-card`, `.disk-list`, `.usage` in Storage), not loose paragraphs.
- Colours always via the CSS tokens on `:root`. Both themes (light = morning mist, dark = evening) must keep working.
- Everything that comes from the server goes through `esc()` before it goes into `innerHTML`.
- **Content Security Policy** (`pageCsp` in server.js for the pages, `API_CSP` for everything else, a sandbox for files opened in the browser in `lib/files.js`): no inline `<script>` and no `on…=` attributes in HTML (also not in `innerHTML` strings); use `addEventListener`. Scripts only from `public/`. `style="…"` attributes are allowed. A new external source (font, script, API the browser calls) must be added to `pageCsp`.
- Don't use `confirm()`/`alert()`. Use the own `ask()` dialog in `app.js` (with a third argument you get a checkbox and `ask()` returns `{ checked }`).
- Destructive actions (stop, shut down, delete) always ask for confirmation first.
- Names on disk that existing installs already use stay as they are (e.g. the Dutch folder names of older backup tasks, `/etc/issue.d/homebaseos-wachtwoord.issue`).
- MajaOS was called HomeBaseOS (versions up to 0.5.0); MajaOS started again at 0.1.0 (first pre-release 0.1.0-beta.1). `deploy/rename-majaos.sh` moves an older server once (folders moved with a symlink at the old path; units, Samba, apt and issue files renamed), run by `lib/update-helper.sh` (rollback goes back to `homebaseos.service`) and `install.sh`. Keep reading the old names: `homebaseos.*` labels (`ownLabels` in lib/docker.js), the network label `homebaseos=1` and the Docker network `homebase` (`ensureMajaNetwork`). The GitHub repo is `lennertvh1/MajaOS` (was `lennertvh1/homebaseos`; the rename script updates `UPDATE_REPO` in the env file).

## Known uncertainties

- The ISO hasn't really been built or booted yet: the menu changes and md5sum.txt were tested with the files of the real Debian 13.7 netinst, but xorriso (replay), the preseed in the initrd (GNU cpio), the live system (`--live`) and installing Debian from that screen not yet. The installer screens are clickable in the demo at `/install.html`. First real test: a UEFI VM with the `--live` ISO.
- *Update now* was tested with simulated systemctl/curl (success and rollback) and a real download from GitHub, not yet on Debian itself. Releases must contain `lib/update-helper.sh` and have the same version in `package.json` as the tag.
- Two-step verification: the blocking after wrong attempts and the link still to be confirmed are in memory (gone after a restart). Behind a reverse proxy MajaOS sees the proxy's address, not the visitor's (X-Forwarded-For is deliberately not trusted).
- **Not yet tested on a real Debian 13 server.** The parsers are tested with sample output, the commands themselves not yet.
- `virsh domstats` for VMs that are off: vCPU and memory then come from the domain XML (`configInfo`, 60 s cache).
- `virt-install --osinfo linux2022` / `win11`: depends on the osinfo-db in Debian 13.
- `undefine --nvram` leaves the TPM state of Windows VMs (in `/var/lib/libvirt/swtpm`).
- The app store converts templates made for Unraid. All 3956 Docker templates from the feed give valid YAML (tested), but not every app will work without changes (own networks, missing databases, Unraid-specific paths).
- The compose form relies on the JSON shape of `docker compose config` (tested with sample output, not yet with a real compose version). If reading fails (old compose, `${VARIABLES}` in ports), it falls back to the text mode. The same goes for `draft`/`installCompose` (advanced install) and the progress parsing of `--progress plain` (`jobLog`), which are tested with sample output only.
- Moving app data (`lib/migrate.js`) and the default folders are tested with the demo and `replacePath`, not yet with real `rsync`, `zfs create` and `docker compose`. An app without a compose file on the server (`docker run`, Portainer) doesn't move along.
- Without an account anyone who reaches the server can create the first account. The live installer makes the account itself, so this only applies to installs with `install.sh` on a bare Debian or the non-live ISO: create it right after the installation.
- The installer's account was tested with the demo and `iso/serve.js` on macOS, not yet on Debian: to check there `openssl passwd -6 -stdin` (LibreSSL on macOS doesn't have `-6`), `chpasswd -e` in the chroot, and the console login with sudo.
- Shared folders are tested up to and including the Samba file and the checks, not yet with a real Samba (`testparm`, `smbpasswd`, `useradd`).
- The terminal on the server is tested up to and including the WebSocket and the security, not yet with util-linux's `script` itself (macOS has a different `script`).
- VM hardware, VM networks and the console are tested with sample XML and a simulated VNC server (noVNC → `lib/websocket.js` → RFB 3.8 with a VNC password), not yet with real libvirt/QEMU. PCI passthrough needs IOMMU (AMD-Vi on in the BIOS); libvirt binds the device to vfio-pci itself (`managed='yes'`). If you pass the GPU through, Ollama doesn't have it while the VM runs.
- Docker networks are tested with sample output of the Docker API, not yet against a real Docker. With macvlan/ipvlan the server itself can't reach the apps (a Linux limitation) unless the shim is on (`lib/macvlanshim.js`, tested with a simulated `ip` only: to check on Debian that the routes win over br0's own subnet route, and that ifupdown reloads don't fight the link); Docker refuses a second macvlan on the same card with the same subnet.
- Changing the network is tested with sample files, not yet on a real server. Confirming only works while MajaOS runs (the rollback is a timer in the process).
- The Community Apps feed has no explicit licence. Fine for own use; ask before publishing.
- Backups are tested with a simulated `rclone` and `zfs` (signing in via 127.0.0.1:53682, tasks, progress, restore, encryption), not yet with the real rclone or real cloud services. To check: the JSON log lines with `stats` (`--use-json-log -v --stats`), the output of `rclone authorize` in Debian 13's rclone version, and whether rclone's `/auth` link really redirects. Without a Debian package: install rclone from rclone.org. Passwords in rclone.conf are only "obscured" (reversible), the file is 0600.
- The backup app is tested with the real Kopia (self-built, v0.23.x) on macOS: creating the repository, policy, `server start` with `--random-password --random-server-control-password --no-ui` and our certificate (EC P-256 must have `ec_param_enc:named_curve`, otherwise Go refuses it), `server user add --user-password`, SIGHUP (a new user only works after it), connecting and a backup of a device, `snapshot list --all --json`, and the whole pairing via the MajaOS Backup app against `server.js` (with a simulated `systemctl` and without ZFS). Not yet on Debian itself (systemd unit, `zfs create`, the kopia.io package source). A device's password is briefly on the command line (`--user-password`), the repository password isn't.
- VM snapshots and backups of apps and VMs are tested with sample output and in the demo, not yet with real libvirt/QEMU and Docker. To check on Debian 13: external snapshots with memory for UEFI VMs, `snapshot-revert`/`snapshot-delete` of external snapshots, `virsh backup-begin` (push) and the output of `domjobinfo --bytes`, and restoring an app (tar with `--same-owner`).
- Time Machine via Samba needs `fruit:time machine` (on) and `vfs objects = fruit streams_xattr` (also on); tested up to the Samba file. The quota is a ZFS quota: Time Machine sees it as the size of the disk.
- Moving from Unraid is tested with sample files of the stick (cfg, passwd, templates, libvirt XML), sample lsblk output and in the demo, not yet with a real Unraid stick and array. To check: the cfg keys of current Unraid versions (shareSecurity, shareReadList/WriteList), xfs read-only mounts of an array that wasn't stopped cleanly, a btrfs cache pool with two SSDs, libvirt.img as a loop mount, and SnapRAID's first sync over xfs disks that are already full.
- Pools with mixed disks were tested in QEMU with three virtual disks (4, 2 and 6 GB): creating, mergerfs over the data disks, fstab, SnapRAID sync and scrub, a shared folder on the pool, refusing and doing a removal. Replacing a disk (`snapraid fix`, rsync, fstab swap) is tested with the checks and in the demo only. Not yet with real disks, spun-down disks or a failing disk.
- Fan control is tested with a simulated hwmon folder and in the demo, not yet on the B550/X570 board itself. To check there: which chip it has (nct6775 family or it87; newer Gigabyte boards may need an it87 driver that isn't in Debian's kernel), whether `pwmN_enable=1` is accepted, and that `ExecStopPost` really gives the fans back to the BIOS.
- Disk sleep is tested with sample output of `/proc/diskstats` and `hdparm -C` and in the demo, not yet with real disks. To check on the server: that `hdparm -y` works for the disks (also behind a USB bridge or HBA), that diskstats really doesn't count `hdparm -C`/smartctl/drivetemp, and what keeps a pool awake (ZFS writes nothing on an idle pool, but apps or VMs on it do).
- `smartctl -n standby` gives no temperature for sleeping disks. The interface then shows "Standby".
- The UPS (NUT) is tested with sample output of `upsc`, `upsc -l` and `nut-scanner` and in the demo, not yet with a real UPS or Debian's NUT 2.8 units. To check on Debian 13: the unit names (`nut-driver-enumerator`, `nut-driver.target`, `nut-server`, `nut-monitor`), which package has `nut-scanner`, `upsmon -c fsd` as primary and that a shared UPS works from Home Assistant.
- ZFS packages (`zfs-dkms`) build a kernel module: after a kernel update DKMS has to build again.
