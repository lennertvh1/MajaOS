# HomeBaseOS

A simple management system for a home server in the style of ZimaOS/HexOS. It runs as root (systemd service) on **Debian 13** and manages **ZFS**, **KVM/libvirt** and **Docker** directly, plus optionally **Ollama**. Unraid is no longer used.

## The owner's situation

- New home server "Freddy": Ryzen 7 5700X + B550/X570 with ECC, 32 GB DDR4 ECC UDIMM, RTX 3060 Ti (8 GB), 2.5G network (10G later).
- Disks: 4× 2 TB HDD and 2× 512 GB SSD (intended as raidz1 pool `tank` and a mirror for apps and VMs; the docs and demo call it `fast`).
- About 20 Docker containers (Compose) and one VM with **Home Assistant OS**. Ollama runs as a container with the GPU.
- The owner develops on **macOS** in VS Code and speaks **Dutch (Flemish)**: talk to the owner in Dutch. The project itself (code, comments, docs, release notes, commit messages) is in English.

## Architecture

- `server.js`: Node 18.11+, **no dependencies** (built-in modules only). Serves `public/`, a JSON API under `/api/*`, auth and the Ollama proxy. Without an account and without `APP_PASSWORD` it is in **setup** (`needsSetup()`): all endpoints return 401 except `/api/config` and `/api/setup` (first account, only while there is none, with an origin check). `passwordEnabled()` = `APP_PASSWORD` or an own password. After starting it runs `vms.bootAutostart()` and `paths.detect()`. Ollama unreachable (ECONNREFUSED, 4 s time-out) → 503 with `notRunning: true` (`ollamaDown`); `e.data` of an error goes along in the JSON response.
- `lib/system.js`: `run()` (execFile without a shell, `LC_ALL=C`, error message from stderr), CPU/RAM from `/proc` (the ZFS ARC doesn't count as used), uptime, OS name, `nvidia-smi`.
- `lib/docker.js`: Docker API via `/var/run/docker.sock`. Own settings per app (WebUI address with `[IP]`/`[PORT:n]`, icon) in `DATA_DIR/apps.json` by container name, so they survive a restart or update. The console runs each command separately via `docker exec … sh -c EXEC_SCRIPT` and returns the folder after `\n\x01`. Logs are demultiplexed. *Update* = `docker compose pull` + `up -d` based on the compose labels (`updateTarget`), run as a job by `appstore.startUpdate` with the same progress and log as installing; afterwards `afterUpdate` checks that image again. The latest update job per app (by container name, kept an hour) is in `/api/apps` as `updateJob`. In the browser: a bar on the tile (`progHtml`, class `updating`, instead of the pulse of other actions), one poller for all running updates (`watchUpdates`), and the log in a window (`updateLogWindow`: click the tile while it updates, or *Update progress / Update log* in the menu). Own labels: `homebaseos.icon`, `homebaseos.webui`. Updates: `checkUpdates` compares the digests of the local image (`RepoDigests`) with the digest of the tag in the registry (`lib/registry.js`, HEAD on `/v2/<repo>/manifests/<tag>`, anonymous token via WWW-Authenticate). Result per image ref in `DATA_DIR/updates.json`; 2 min after start and every 6 hours, or right away via `/api/apps/check-updates`. After Update that image is checked again.
- `lib/xml.js`: small XML reader/writer for libvirt XML. Keeps order, whitespace and comments (reading and writing unchanged = exactly the same); `append` indents new elements neatly.
- `lib/vmhw.js`: hardware of a VM in the domain XML. `parseHardware` (nics, disks, cdroms, boot, hostdevs as `usb:vvvv:pppp`/`pci:0000:0a:00.0`, cpuPins), `applyHardware` (only what is in `change`: network cards by MAC, adding/detaching disks, cd-rom with possibly a new SATA drive, boot via `<boot order>` per device, hostdevs, `cputune/vcpupin`, clipboard channel `qemu-vdagent`), `validateHardware` against the server's options. Cards of another type (e.g. `direct`) get `locked`. The server's devices: `lsusb` (without hubs), `/sys/bus/pci` + `lspci -Dmm` (IOMMU group, driver), CPU topology from `/sys/devices/system/cpu`.
- `lib/vmnet.js`: VM networks. libvirt networks (`net-list/net-dumpxml/net-info`, creating as NAT or isolated with DHCP in the second half of the subnet, `net-define` + `net-autostart` + `net-start`) and the server's bridges. Deleting only if no VM uses it; the subnet must be private and may not overlap with the server (also docker0/virbr).
- `lib/websocket.js`: minimal WebSocket server (RFC 6455): `proxyToTcp` passes the console (noVNC) on to QEMU's VNC screen on 127.0.0.1, `acceptWebSocket` is a plain WebSocket (for the terminal). `server.js` does the upgrade on `/api/vms/:id/vnc` and `/api/terminal` with the same sign-in and origin check.
- `lib/terminal.js`: terminal on the server (root shell). `script -qfec "stty rows R cols C; exec bash -l" /dev/null` (util-linux) creates the pseudo-terminal; messages from the browser are JSON `{t:'d', d}` (keys) or `{t:'r', cols, rows}` (size → `stty -F /dev/pts/N`). Each connection asks for a one-time ticket (`/api/terminal/ticket`, 60 s), with the password if *Security* asks for it. Opening and closing are logged. In the browser: `public/terminal.html` + `terminal.js` with xterm.js from `public/vendor/xterm` (6.0.0 + addon-fit, unchanged, MIT), in the same window as the console (`openTerminal`) or separately.
- `public/console.html` + `public/console.js`: console (`console.html#<name>`) with noVNC from `public/vendor/novnc` (1.7.0, unchanged, MPL-2.0; only `core/` and `vendor/pako`). Opens in HomeBaseOS as an iframe in `#conWin` (`openConsole`); *Pop out* opens the same address with `window.open` as a popup and calls the parent's `TB_closeConsole`. Ctrl+Alt+Del, typing text, fit/real size, full screen. **Paste**: Cmd/Ctrl+V is held back from noVNC in the capture phase, focus briefly goes to an invisible text box (`#cPasteSink`) so the paste event arrives in every browser, and the text is typed letter by letter as keysyms (+ `clipboardPasteFrom`). **Copying from the VM**: noVNC's `clipboard` event (needs `qemu-vdagent` + spice-vdagent in the guest) → `navigator.clipboard` when allowed (https), otherwise a button with `execCommand('copy')`. A simulated screen in the demo.
- `lib/vms.js`: libvirt via `virsh -c qemu:///system`. List from `virsh domstats` (CPU% = delta `cpu.time` relative to the VM's own vCPUs, RAM from balloon statistics). IP addresses of running VMs with `virsh domifaddr --source agent|lease|arp` (the first that gives something, kept 30 s). Editing = changing the domain XML (`editDomainXml` + `vmhw.applyHardware`) + `virsh define` (with `--security-info`, otherwise the VNC password disappears). New disks with `qemu-img create` in `VM_DIR/<name>/`, enlarging with `qemu-img resize` (off) or `virsh blockresize` (on); swapping an ISO also works live on a running VM (`change-media`). With pinned cores the number of vCPUs follows from the cores. Creating with `virt-install` (UEFI, host-passthrough, VNC with a password). Deleting = `undefine --nvram`; disks are only erased inside `VM_DIR`. Automatic start + delay is in `DATA_DIR/vms.json`; libvirt's autostart is then turned off. A marker in `/run/homebaseos` prevents starting twice.
- `lib/paths.js`: where folders go: `appdata`, `vms`, `isos`, `shares` in `DATA_DIR/paths.json`, falling back to the old variables `APPDATA_DIR`, `VM_DIR`, `ISO_DIR`, `SHARES_DIR`, otherwise `null` (`shown()` then gives `/<pool>/…` to display; installing refuses with a message). `createDefaultFolders` creates the datasets appdata, media, backups, vms, isos on a new pool (appdata/media/backups owned by `APP_UID:APP_GID`); `adoptPool` puts whatever had no (existing) place yet on that pool (shares = the pool itself); `detect` (at startup, in Settings → Storage and in the app store as soon as the folder is missing: `ensureAppdata`) looks for an existing folder (`pickFolder`) for whatever isn't set or no longer exists: for appdata first where the containers have their bind mounts (`appdataFromMounts`: …/appdata/<app>), then a dataset with that name (also deeper), then a plain folder `<pool>/appdata`. In Settings → Storage you can also point to an existing folder yourself (*Existing folder…*, `migrate.usePath`: nothing moves). The app store and `vms.js` read the folders every time (`APPDATA_DIR()`, `VM_DIR()` are functions).
- `lib/migrate.js`: Settings > Storage (`storagePane` in app.js). `overview` (paths, pools via `zfs list -d0`, apps with a bind mount in the app data: per compose project, and `manual` without compose or with a compose file that isn't on the server, as with Portainer; `groupContainers`), `setLocation` (vms/isos/shares on a pool, creating the dataset if missing, files don't move along) and `migrateAppdata`: one job in memory (steps prepare → stop → copy → compose → start → done): dataset `<pool>/appdata`, stop compose projects, `rsync -aHAX --numeric-ids --info=progress2` (percentage from the output), replace paths in the compose files (`replacePath`: full paths only, `.bak`), `paths.save`, `up -d --force-recreate` (or `--no-start` if the project wasn't running). If it fails before switching over, the apps start again with the old folder. The old folder always stays; folders with the same name in the target folder → 409.
- `lib/appstore.js`: catalogue from the Unraid Community Apps feed (`applicationFeed.json`, cached 24 h in `DATA_DIR/appstore.json`). `normalizeFeed` removes plugins/deprecated/blacklist, cleans up BBCode and computes popularity (one template per image, the name must fit the image) and `featured`. `prepareFields` translates Unraid paths (`PATH_MAP`), 99:100 → `APP_UID:APP_GID`, `TZ`, and fills an empty `/config` with `APPDATA_DIR/<name>` (`auto: true`). `buildCompose` creates `compose.yaml` (own YAML writer: strings as JSON) with labels `homebaseos.store`, `homebaseos.data`, `homebaseos.icon`, `homebaseos.webui`. `iconFor` gives apps without a `homebaseos.icon` label an icon: first from the catalogue (same image), otherwise from dashboard-icons by name (checked once, remembered in `DATA_DIR/icons.json`). Installing = a job (`startJob`) that runs `docker compose pull` + `up -d` in `STACKS_DIR/<name>`, and cleans up on an error. `jobLog` updates the output of `--progress plain` like a terminal: one line per layer, container or network, updated in place; `jobProgress` derives the percentage from it (downloading 3–85 %, starting 85–99 %). In the browser: `jobHtml`/`drawJob` (bar, step, *Details* with the output, opened on an error). **Own app**: `normalizeImage` turns a name, `docker pull …` or a link (Docker Hub, GitHub package, Quay) into an image; `inspectImage` reads with `registry.imageConfig` (manifest → right architecture → config blob, without downloading) the ports (EXPOSE), folders (VOLUME) and proposes PUID/PGID/TZ, a free port, folders in `APPDATA_DIR/<name>`, a WebUI address and an icon; `installCustom` builds the compose file (`buildCustomCompose`, label `homebaseos.custom=1`) and uses the same job. In the browser the form reuses `composeFormMount`. **Advanced** (app store) and *Fields/Code* (own app): `draft` creates a draft (`{store, …}` like installing, `{custom}`, `{text}` or `{text, form}`), reads it with `composeform.loadProject` and returns `{text, form, formError, dockerNetworks}`, so fields and code are always the same file via the server (unknown keys stay). `installCompose({name, text})` writes exactly that text to `STACKS_DIR/<name>/compose.yaml`, checks it with `docker compose config`, creates missing bind folders under the app data (owned by `APP_UID:APP_GID`) and starts the same job. *Data folder* (`__datadir`, suggestions from `folders` = mount points of the datasets): all paths below it move along (`rebasePath` in app.js). In the browser: `advancedEditor`, `dataDirHtml`, `advToggleHtml`. Network: `templateNetwork` (e.g. `br0`) is suggested if such a Docker network exists; when installing the user chooses `network` + `ip`, and can add `extraPorts`. Port fields are always editable. With host or an own address (macvlan/ipvlan) Docker can't remap ports: a changed template port goes to the app's own port setting (a Variable with "port" in its name and the same value, e.g. WEBUI_PORT) and `homebaseos.webui` follows (`[PORT:n]`); without such a setting there is a warning. Only *+ Port* (extra ports) switches the browser to the default network. A fixed IP on the default network: `dockernet.networkFor`/`formNetwork` put the app in the shared bridge network **homebase** (`ensureHomebaseNetwork`: the first free of 172.30.0.0/16, 172.29.0.0/16, 10.250.0.0/16, label homebaseos=1; `checkFreeIp`: in the subnet, not the network/broadcast/gateway address, not used by another app); refused for a compose file with several services, which would be cut off from each other. **Own address in my home network** (choice `@lan`, `LAN_CHOICE`): `ensureLanNetwork` uses an existing macvlan/ipvlan on the home network's card, or creates macvlan `lan` itself (card with the default route, its subnet, the router as gateway, IP range = the top /27 via `lanRange`); `lanInfo` (`GET /api/docker-networks/lan`) also suggests a free address (`suggestLanIp`: in the range, not used by an app, not in `ip neigh`, no answer to a ping). In the browser `suggestLanIp` fills in the IP field (install form and compose form). With macvlan/ipvlan (own address) there are no ports on the server and `webui()` in `lib/docker.js` fills in the own address for `[IP]` and the app's port for `[PORT:n]`. On host also the app's port; on bridge the published port (TCP first), and if `[PORT:n]` isn't mapped anywhere, the only published TCP port. If the container list gives no ports, they come from inspect (`portsOf`).
- `lib/layout.js`: layout of the home screen in `DATA_DIR/layout.json`: `{items: ["<container name>" | {folder, name, apps: [...]}]}`. `validateLayout` allows each app only once, turns a folder with one app back into a plain app and drops empty folders. In the browser: `homeItems()` (new apps at the end, apps that are gone removed), dragging with pointer events whenever the grid is showing (a click that does not move still opens; middle of an app = make a folder, edge = before/after, dragging out of the folder panel = out of the folder; holding a widget shows the cell grid), folder panel `#folderPanel` (name, Ungroup) and in the menu *To folder…* / *Out of folder*. When searching or filtering it is a plain list without folders. **List view** (*Grid / List* next to the filters, `S.view`, `localStorage tb-app-view`, per device): `appRow` per app (icon, name and image, status, address and the other ports, folder, quick buttons Open/Start/Restart and the menu) in the home order (apps in a folder right after each other); no arranging or dragging there. In the same file: `widgets {order, hidden}` for the widgets on the left of the dashboard (`applyWidgets`, *Customize widgets*: ↑/↓, dragging, eye). Each widget is in a `.widget-slot[data-widget]` (clock, sys, storage, shares, backup, ai, vms).
- `lib/composeform.js`: a compose file as a form (like Unraid's container form). `docker compose config --no-interpolate --no-normalize --no-path-resolution --format json` reads the file, `serviceForm` turns it into fields (image, restart, network, privileged, ports, volumes, env, devices, labels), `applyServiceForm` writes them back into only that service. Network: `network` is `''` (default), `host`, `none`, the name of one custom network (with an optional `ip` → `ipv4_address`) or `*` (several networks: stay unchanged). A network that isn't in the file is added as `external: true`; external networks no service uses anymore disappear. `appSettings` passes the choices in `compose.dockerNetworks`. Complicated mounts (tmpfs, propagation, ports with unknown keys) get `locked` and stay unchanged. Ports with `mode: host` are editable and written back in the long syntax. Everything the form doesn't know stays. The file is rewritten with `lib/yaml.js` (comments disappear, a `.bak` stays).
- `lib/yaml.js`: small YAML writer (strings as JSON; null, `{}` and `[]` are kept).
- `lib/auth.js`: account and two-step verification. Account: `createAccount(user, pw)` (only without a password; user name `^[a-z][a-z0-9._-]{1,31}$`, lowercase), `user` in `auth.json`, `checkUser` (without a user name, for older installs, only the password counts). Signing in sends `{user, password}`; `/api/config.loginUser` says whether the screen asks for a user name. TOTP (RFC 6238, SHA-1, 6 digits, 30 s, ±1 step; a used counter doesn't count again) with `node:crypto`. `DATA_DIR/auth.json` (0600): `{mfa: {enabled, secret (base32), lastCounter, recovery: [sha256], since}, sessionsAfter}`. Recovery codes `xxxxx-xxxxx`, stored only as a hash, each one once. Linking: `beginSetup` (secret only in memory, 15 min) → `finishSetup(code)` (sets `sessionsAfter`: all older sessions are invalid, `validToken` in server.js checks that). Signing in in two steps: `/api/login` returns `{mfa, pending}` with MFA (one-time, 5 min, max. 5 wrong codes), `/api/login/mfa` sets the cookie. Per IP: 10 failures in 10 min → 5 min `429` (in memory). In the browser: the sign-in screen (`loginStep`, `setRecoveryMode` in app.js; six digits confirm by themselves) and `mfaSection` in Security. The QR code is made by `public/qr.js` (own encoder, byte mode, level M, versions 1–10; tested with `BarcodeDetector`). The demo computes real TOTP codes with `crypto.subtle` (password `demo`; *Sign out* shows the sign-in screen).
- `lib/datetime.js`: date, time and time zone (Settings > General, `dateTimeSection` in app.js). Reads `timedatectl show` / `show-timesync` (`parseKeyValues`) and `timedatectl list-timezones`; sets with `set-timezone`, `set-ntp` and `set-time` (only when NTP is off; `parseLocalTime`). Own time servers in `/etc/systemd/timesyncd.conf.d/homebaseos.conf` (`[Time] NTP=…`, empty = file removed = Debian's default) + a restart of systemd-timesyncd. `hostTimezone()` reads the `/etc/localtime` link (Node remembers the time zone from when it started) and is also used by the app store (TZ) and About. The time format (`clock`: auto\|24\|12) is in `settings.json` and `/api/config`; `clockOpts()` in app.js gives the options for `toLocale…String`.
- `lib/release.js`: Software update (Settings > Software update, `updatePane` in app.js). Looks for new versions among the GitHub releases of `UPDATE_REPO` (default `lennertvh1/homebaseos`, private → `UPDATE_TOKEN` needed, fine-grained with read access to Contents). `normalizeReleases` (no drafts, beta only with `updateChannel: beta`, only github.com links), `compareVersions` (semver with -beta), `summarize` (newer, installed, history relative to `package.json`). Raw list + error in `DATA_DIR/release.json`; channel **dev** (`updateChannel: dev`, for test servers): `checkDev` reads the newest commit of `DEV_BRANCH` (default `dev`, `/repos/:repo/commits/<branch>`), its package.json version and the commits since the installed one (`/compare`), and `devSummary` turns that into the same shape as releases (version `<x.y.z>+dev.<sha7>`, the commits as notes). The installed commit is in `build.json` next to server.js (`currentBuild`), written by the updater for a dev build and removed for an official release and by `install.sh`. `deploy/install-branch.sh [branch]` puts a server on a branch the first time (download with UPDATE_TOKEN, install.sh, build.json, channel dev; `main` = back to stable); checking 1 min after start and every 12 hours if `updateCheck` is on. In the browser: `loadUpdate` (at start and every 30 s) puts a red dot on Settings (`#updDot`) and the tab (`#updTabBadge`) and shows a notification once per version (`localStorage tb-update-seen`). Release notes go through `mdToHtml` (first `esc()`, then limited Markdown). *Update now*: `lib/updater.js` downloads the tag's tarball (`/repos/:repo/tarball/:tag`, follows the redirect without the token), unpacks it in `DATA_DIR/update/new`, checks it (`package.json` version = release, `node --check` on server.js and lib/*.js) and then starts `lib/update-helper.sh` (first copied to `DATA_DIR/update/helper.sh`) as its own unit with `systemd-run --collect`, so it survives the restart. The helper: backup copy in `DATA_DIR/update/previous` (server.js, package.json, lib, public, deploy + service file), replace files, update the service file if it changed, `deploy/upgrade.sh` (system packages, may run more than once), `systemctl restart`, wait 45 s for `/api/config`; if that fails, everything back (`rolledback`). Progress (step, percent, message, reason, bytes/total) in `DATA_DIR/update/status.json`; the browser reads `/api/update/progress` (`updateProgress` in app.js) and keeps asking while the server is briefly gone. Only possible as root on Linux, not from a git folder (`canUpdate`). Always use braces for variables in the helper's messages (`${OLD}…`): otherwise bash reads the `…` as part of the name. Note: `data-upd` is already taken by app updates, here it is `data-sw`.
- `lib/debian.js`: updates of Debian itself (Software update > *Debian (the system)*, `debianSection` in app.js). `status`: waiting updates from `apt list --upgradable` (`parseUpgradable`, security = a `-security` suite), automatic updates (`unattended-upgrades` installed + `APT::Periodic` in `/etc/apt/apt.conf.d/20auto-upgrades`, `parseAutoConf`; last run from `unattended-upgrades.log`, `parseUuLog`), restart needed (`/var/run/reboot-required(.pkgs)` or a newer kernel in `/lib/modules` than `uname -r`, `sortKernels`) and whether ZFS is built for that kernel (`dkms status`, `parseDkms`; `zfsReady` false = don't offer Restart now). Actions `check|upgrade|auto-on|auto-off` run `lib/apt-helper.sh` (copied to `DATA_DIR/debian/`) as its own unit with `systemd-run`, because needrestart may restart HomeBaseOS during apt; state in `DATA_DIR/debian/status.json`, output in `log.txt`. `auto-on` installs unattended-upgrades + needrestart and writes `/etc/apt/apt.conf.d/52homebaseos` (never an automatic reboot) and `/etc/needrestart/conf.d/homebaseos.conf` (restart services automatically, never docker/containerd). `install.sh` and `deploy/upgrade.sh` run `auto-on` once (as long as `52homebaseos` doesn't exist), so turning it off stays off.
- `lib/onboarding.js`: welcome wizard (the first time without sign-in, in setup; otherwise after the first sign-in) (`DATA_DIR/onboarding.json` {done, finished, skipped}; `/api/config` returns `onboarding: true` as long as it isn't finished, only to whoever is signed in). In the browser: `#onbWin` + `openOnboarding`/`onbSteps`/`onbGo` in app.js; while it is open, `body.onb-open` hides the dashboard (only the background). In setup `boot()` only starts the wizard (no `startDesk`, the server's language doesn't apply yet) and `onbFinish` starts the dashboard afterwards. Steps: welcome (language → `location.reload()` and continue at step 2 via `sessionStorage tb-onb-step`, theme; in setup the language goes along with `/api/setup`), account (in setup: user name + password → `/api/setup`, only then `/api/onboarding`; no Skip or Set up later) or password (older installs, `/api/password`), server (hostname via `/api/network/hostname`, time zone via `/api/datetime`, a suggestion from the browser if the server is on UTC), storage (pools + free disks; without a pool the `poolForm` form (inline) is there right away, with pools behind *Create another pool*; with ticked disks Next is called *Create pool* and creates the pool, then the step stays with the new pool), two-step verification (`mfaSection` with `box.dataset.noHead`), done (overview + shortcuts). *Skip* is on every step except welcome, account and done. *Set up later* finishes with `skipped`. Open again in Settings > General. In the demo `localStorage tb-onboarded` remembers it; until then the demo starts like a new server (setup, account in `localStorage tb-demo-user`, the password only in memory, `demo` always works).
- Own password: `auth.setPassword` stores a scrypt hash in `auth.json` (`password {salt, hash, changed}`) and sets `sessionsAfter` (other sessions signed out). Once it exists, `checkPassword` in server.js only checks that hash; `APP_PASSWORD` is still needed to start and applies until the first own password. It can also be changed in Security (`passwordFields`, `wirePasswordMeter`, `submitPassword`). Every `put()` in auth.js must keep the rest of the state (`...get()`).
- `lib/settings.js`: general settings in `DATA_DIR/settings.json` (the language, default `en`, and Security: `terminal`, `terminalPassword`, `ssh`; applies to everyone, also in `/api/config`). The accepted languages are read from `public/lang/languages.js` (`LANGUAGES`). Making things less strict (terminal on, SSH on, or no longer asking the password) requires the password (`checkPassword` from `server.js`). SSH itself is `lib/ssh.js`: `systemctl enable|disable --now ssh` (OpenSSH). The setting defaults to off; at startup HomeBaseOS applies it, and `install.sh` installs OpenSSH and then disables it unless `settings.json` already says `"ssh": true`. The browser keeps the theme itself (`localStorage`).
- `lib/about.js`: About page: DMI (`/sys/class/dmi/id`), ECC (`/sys/devices/system/edac`), GPU, versions of Docker, Compose, ZFS, libvirt and QEMU.
- `lib/dockernet.js`: Docker networks via the Docker API (`docker()` from `lib/docker.js`, which also sends a JSON body). Bridge, macvlan and ipvlan (`ipvlan_mode: l2`). `validateNetwork` checks the name, subnet/gateway/IP range (CIDR arithmetic without a dependency), the parent card (from `ip -j -d addr`) and overlap with existing networks and, for a bridge, with the home network. Own networks get the label `homebaseos=1`. Deleting only if there are no containers in it; the built-in ones (bridge/host/none) never. The app store uses `resolveNetwork` and `checkIp` for the network choice when installing.
- `lib/network.js`: view the network (`ip -j -d addr`, `ip -j route`) and change it via ifupdown (`/etc/network/interfaces`): card, DHCP or static address, gateway, DNS, bridge `br0`. Applying makes a backup copy in `DATA_DIR/network-previous`, reloads (`ifdown`/`ifup`) and puts everything back after 2 minutes without confirmation. Other `iface` blocks stay unchanged. Hostname via `hostnamectl` (right away, without confirmation).
- `lib/bays.js`: drive bays (which disk sits in which bay of the case) in `DATA_DIR/bays.json`: {count, columns, m2, ssd, slots {"<bay>", "m<slot>" or "s<slot>": {key, label}}}; `m2` = number of M.2 slots for NVMe and `ssd` = number of 2.5" slots, in the same `slots` with keys m1…/s1…. By default all bays are on one row (columns = number of bays, max 12). The storage window gets the class `win-wide` (12 bays side by side, the case in the middle); `openWindow` removes it again. A disk is called `s:<serial number>` (otherwise `n:<name>`), so the layout stays right when sda/sdb swap; `label` keeps model + serial number for when the disk is gone. In the browser: `mountBays` in the storage window, drawn as a NAS case (drawers with vents, handle, status LED and labels for pool and temperature; colours via the tokens `--nas-*`, `--led-off` and `--pool-1..5`). Drag, or tap a disk and then a bay; on a full bay they swap. Clicking the chosen bay again closes the panel.
- `lib/zpool.js`: creating a pool. `poolOptions` (lsblk with partitions, `zpool status -LP`, `/proc/swaps`, `/dev/disk/by-id`) marks per disk `available`/`reason` (in a pool, system disk, mounted, swap) and `warn` (old partitions or a ZFS label: they will be erased). `capacity(layout, sizes)` (usable, protection, unused because of the smallest disk, ~3% slop, number of disks that may fail) is also in `app.js` as `poolCapacity`: keep them the same. `createPool` then creates the default folders (`folders`, on by default; see `lib/paths.js`) and returns `{name, folders, uses, warning}`. In the browser the form is `poolForm(body, opts, bays, {inline, onCreated, onBack, onPick})` → `{submit, picked}`, used by `poolCreateWindow` and the wizard. `buildCreate` checks everything (also `confirm` = name) and builds `zpool create -f -o ashift=12 -o autoreplace=on [-o autotrim=on] -O compression=… -O atime=off -O xattr=sa -O acltype=posixacl -m /<name>` with by-id paths; mirror pairs are paired large with large.
- `lib/disks.js`: details of one disk (`smartctl -a -j`, with `-n standby` unless `wake`): model, serial number, firmware, power-on hours, power cycles, temperature, rotation rate, interface, important sector counters (5, 197, 198, 187, 199, 188), NVMe wear/spare/written, self-tests (also a running one) and all attributes. Start a self-test with `smartctl -t short|long`. Only disks lsblk knows. In the browser: click a bay → panel next to the case (`renderPanel` in `mountBays`), refreshes every 10 s while a test runs.
- `lib/shares.js`: shared folders (Samba), their users and groups. The source is `DATA_DIR/shares.json` ({shares: [{name, path, comment, users {name: ro|rw}, groups {group: ro|rw}, guest, timemachine}], users: [names HomeBaseOS created], groups: [{name, comment, members}]}). Groups are not Linux groups: `effectiveUsers(share, groups)` adds the members of the groups to the folder's users (the highest right counts) and `buildSmbConf` writes that list. A change that would leave a folder without users (deleting a user or group, removing rights) is refused (409). Managed in Settings → Users (`usersPane` in app.js, tabs Users and Groups; `accessOf` shows per folder the right and where it comes from); the Shared folders window refers to it. `buildSmbConf` creates `/etc/samba/homebaseos.conf` (valid users / write list, `guest ok`, `force user/group` = APP_UID/APP_GID so files belong to the same user as with the Docker apps, `vfs objects = catia fruit streams_xattr shadow_copy2`, Time Machine). Hourly ZFS snapshots (`lib/shadow.js`, name `GMT-YYYY.MM.DD-HH.MM.SS`) show up in Windows as Previous Versions; 24 hours, then 14 days, then 8 weeks are kept. A folder without users and without guests is never written (an empty valid users = everyone). `apply` first checks with `testparm -s` on a copy, then writes, puts one include line in smb.conf and runs `smbcontrol smbd reload-config`. A new folder = `zfs create <pool>/<name>` with chown to the app user; an existing folder must be on a ZFS mount point. Users: `useradd --no-create-home --shell /usr/sbin/nologin` + `smbpasswd -a -s` (password via stdin, `run({input})`); deleting isn't possible if someone is the only one with access to a folder. In the browser: a window of its own (`sharesWindow`), via the *Shared folders* button at the top and from Storage.
- `lib/backup.js`: Backups (`backupWindow` in app.js, *Backups* button at the top and the `backup` widget). Three tabs. **Devices** (`method` share or kopia; without `method` = share): with the backup app everything goes through `lib/kopia.js`; with a shared folder `createDevice` creates `<pool>/backups/<name>` (`zfs create -p`, optionally `quota=…G`, chown to the app user) and a shared folder with the same name via `shares.saveShare` (one user rw, Time Machine for `mac`); if the share fails, the dataset goes away again. Deleting removes the share, the dataset only with `?data=1` (`zfs destroy -r`, only `<pool>/backups/<name>`). `lastChange` = newest mtime up to two levels deep (max. 3000 items). **Connections** (rclone remotes) in `DATA_DIR/rclone.conf` (0600, own INI reader/writer `parseConf`/`buildConf`; passwords via `rclone obscure -` on stdin, never on the command line). Kinds in `PROVIDERS` (drive, onedrive, dropbox by signing in; s3, sftp, smb, webdav with fields); new = write + `rclone lsjson` as a test, otherwise removed again. Signing in: `startAuth` starts `rclone authorize <type> --auth-no-open-browser` (listens on 127.0.0.1:53682), fetches the local `/auth` link and gives the redirect (the sign-in page) to the browser; the user pastes the address Google/Microsoft/Dropbox sends back to, `finishAuth` forwards the query to 127.0.0.1:53682 and reads the token (`parseAuthToken`: JSON, or base64 of `{token, …}` in newer rclone). OneDrive gets `drive_id`/`drive_type` from Microsoft Graph (`/me/drive`). Pasting a token (from `rclone authorize` on a PC) and `reconnect` (sign in again, same name) also work. **Tasks** in `DATA_DIR/backup.json` {jobs, devices}: `direction` push\|pull, `mode` copy\|sync, `schedule` {every: manual\|hourly\|daily\|weekly, time, day}, `encrypt` (push only, only when creating: crypt remote `hb-crypt-<id>` around `remote:remotePath`, destination `…:files`, versions `…:versions`), `versions` + `keepDays` (`--backup-dir "<destination> (old versions)/<date>"`, then `rclone delete --min-age` + `rmdirs`), `excludes`, `bwlimit`. Tasks created before 0.6 have no `names: 'en'` and keep the Dutch folder names on the destination (`bestanden`, `versies`, `(oude versies)`; see `targets`): never rename those. `validateJob`: refuses sync/versions to the top folder of an unencrypted destination, pull never into a whole pool. `buildArgs` (`--use-json-log -v --stats 2s --links`), `parseLogLine`/`summarize` for progress and the log. Running tasks only in memory (`live`); `preflight` refuses if the dataset isn't mounted or the source folder of a sync is empty. After pull/restore `chown -R` to the app user. History (20) in the task, log (400 lines) in `DATA_DIR/backup-logs/<id>.json`. Schedule: `tick` every 30 s, `nextRun` in the server's time zone; missed times are caught up once; if the previous run is still going, that time is skipped. *Dry run* = `--dry-run`, *Restore* = `copy` from the destination to a folder on the NAS.
- `lib/kopia.js`: backup app for PCs and Macs (*Backups → Devices*, `kopiaCard`/`kopiaHowTo` in app.js). Kopia server as systemd unit `homebaseos-kopia` (`unitFile`: `--address=0.0.0.0:51515`, own TLS certificate via `openssl req -x509` (EC P-256, 10 years), `--random-password --random-server-control-password --no-ui`: no web interface, `ExecReload` = SIGHUP so changed users apply without a restart, `RequiresMountsFor` the repository). `enable(pool)` the first time: dataset `<pool>/backups/kopia` (0700, must be empty), `kopia repository create filesystem`, global policy (every hour; 10 latest, 24 hourly, 14 days, 8 weeks, 12 months, 3 years; zstd), certificate, unit; returns the repository password once (`repoPassword`). If something fails, everything goes away again. Afterwards on/off = `systemctl enable/disable --now` (repository and users stay). Files in `DATA_DIR/kopia` (repository.config, server.cert/.key, server.env with `KOPIA_PASSWORD` (0600, never on the command line), state.json {enabled, pool, dataset, path}). Each device = Kopia user `<name>@<name>` (lowercase; on the device you fill in that name as Override Username and Override Hostname). Password `newPassword()` (xxxxx-xxxxx-xxxxx-xxxxx, without l/1/o/0) via `server user add/set --user-password`; it is returned only once (`bk.secret` in app.js). Deleting with backups: `snapshot delete … --delete` (space is freed at Kopia's maintenance). Last backup per device from `kopia snapshot list --all --json` (`parseSnapshots`, kept 30 s). **Pairing with the HomeBase Backup app** (fork of KopiaUI in `../homebase-backup`, see `HOMEBASE.md` there): `newPairing(name)` creates a new password and a pairing code (8 characters without I/L/O/0/1, shown as XXXX-XXXX, 15 minutes, one-time, only in memory); `GET /api/backup/pair/:code` (without sign-in, before the sign-in check in server.js, CORS `*`) returns {port, fingerprint, username, hostname, password, nas}; 10 wrong codes per IP in 10 min → 5 min 429 (`usePairing`). A new device gets a code right away; *Pairing code* on a device creates a new one (the device then has to pair again). Download link of the app: `BACKUP_APP_URL` (default the releases of lennertvh1/kopia). By default each user only sees their own backups (Kopia's ACLs are not on). Kopia comes from the kopia.io package source (`install.sh`, and `deploy/upgrade.sh` without an error stopping the update).
- `lib/vmsnap.js`: snapshots of VMs (tab *Snapshots* in the VM window, `drawSnaps` in app.js; carried out right away, Save is hidden there). Always external (`--diskspec <disk>,snapshot=external`, cd-roms `snapshot=no`): internal snapshots don't work with the raw nvram of UEFI VMs. If the VM runs, with memory (`--memspec file=<disk>.<name>.mem`), unless `diskOnly` or the VM has a passed-through device; shut off = `--disk-only`. List via `snapshot-list --topological` + `snapshot-dumpxml` (`parseSnapshotXml`), revert `snapshot-revert`, delete `snapshot-delete` (merges the overlay; libvirt 9.9+). `deleteVm` also erases the whole chain with the disks (`backingChain`, `qemu-img info --backing-chain`) and the `.mem` files.
- `lib/sysbackup.js`: backups of apps and VMs to a folder on the NAS (*Backups → Apps and VMs*, `bkSystem`/`sysJobForm`/`sysRestore` in app.js). Tasks in `DATA_DIR/sysbackup.json` {jobs [{id, name, dest, apps ['compose:<project>'\|'container:<name>'], vms, stopApps, vmMode live\|shutdown, keep, schedule, …}]}; schedule and `nextRun` from backup.js. Each run `<dest>/<YYYY-MM-DD_HHMMSS>/` with `manifest.json` (0600), `apps/<app>.tar.gz` and `vms/<vm>/` (domain.xml with `--security-info`, nvram, `<disk>.qcow2`). An app = a compose project (`parseUnits` on `/containers/json`): included are the compose files + `.env`, bind mounts inside the app data or the project's folder, and volumes; other bind mounts are listed in `skipped` (e.g. /tank/media, docker.sock). `stopApps` stops the running containers via the Docker API and starts them afterwards. VM off: `qemu-img convert -O qcow2` (flattens snapshots); on + live: `virsh backup-begin` with a push XML (`backupXml`), progress from `domjobinfo --bytes` (`parseJobInfo`); on + shutdown: shut down (max. 5 min), copy, start. `prune` keeps the newest `keep` folders with a manifest. One backup at a time; stopping kills tar/qemu-img or runs `domjobabort`. Restore: app = stop the containers, rename the current folders to `<folder>.before-restore-<date>`, unpack the tar, start; VM = must be off and without snapshots, disks moved aside and `qemu-img convert` to the old format, nvram back, `virsh define` if the VM no longer exists.
- `lib/storage.js`: `zpool list/status -LP`, `zfs list -Hp`, `lsblk -J`, `smartctl -n standby -j` (don't wake sleeping HDDs).
- `public/index.html`, `public/style.css`, `public/app.js`: vanilla HTML/CSS/JS, no build step. Apps: a left click opens the WebUI (`openAppUrl`), a right click or ⋯ opens the menu (`openAppMenu`, keyboard: arrows/Home/End/Escape) with actions, logs, console and settings. The VM page is at `#vms` and the app store at `#store` (hash routing via `route()`), the rest are windows (`openWindow`). Settings is a window of its own with a sidebar (`#setWin`, like System Settings on macOS): `#settings`, `#settings/storage` (Storage), `#settings/network`, `#settings/docker` (Docker networks), `#settings/vmnet` (VM networks), `#settings/security` (Security) and `#settings/about` open it above the page remembered in `pageHash`. Closing always goes through `closeSettings()`, which restores the address right away.
- `public/lang/`: translations. `languages.js` lists the languages (`window.TB_LANGS = {code: {name, locale}}`, English is built in) and loads `<code>.js` for each one with `document.write`, so the dictionaries are there before the page's scripts run; `nl.js` = `window.TB_LANG.nl = {"English text": "Dutch text"}`. `app.js`, `console.js` and `terminal.js` read `window.TB_LANG`; the chosen language is in `localStorage tb-lang` and `settings.language`.
- `public/demo.js`: a **demo adapter in the browser** that mimics exactly the same endpoints and response shapes as `server.js`. **Whenever you change an endpoint, also update `demo.js`**, otherwise the demo breaks.
- `iso/`: installation ISO. `build-iso.sh` (Linux: xorriso, GNU cpio) takes the official Debian 13 netinst (latest 13.x, checked with SHA256SUMS), puts `preseed.cfg` in a copy of the initrd (`/homebaseos/initrd.gz`, so language and keyboard are answered too), adds HomeBaseOS (`git archive HEAD`, or `--worktree`), puts two entries at the top of `boot/grub/grub.cfg` (UEFI; `x86_64-efi/grub.cfg` does `source /boot/grub/grub.cfg`) and in isolinux (`homebaseos.cfg`, `menu default` removed from `gtk.cfg`), updates `md5sum.txt` and writes with `xorriso -boot_image any replay` (same BIOS/UEFI/USB setup). The installer runs in English (`en_US.UTF-8`), with country BE, Belgian keyboard and time zone Europe/Brussels. Preseed deliberately leaves open: the disk, the confirmation before erasing and the password of user `homebase` (test/iso.test.js guards that). `late.sh` (late_command) unpacks HomeBaseOS in `/opt/homebaseos-setup` and enables `homebaseos-firstboot.service`; `firstboot.sh` runs `install.sh` at the first boot (`--nvidia` if `homebaseos.nvidia=1` was on the kernel line), and puts the address on the screen via `/etc/issue.d/` (`\4` = IPv4) asking to create an account in the browser. No password is shown on the screen anymore; an old `/etc/issue.d/homebaseos-wachtwoord.issue` (from older installs, the name stays) disappears at `/api/setup` or `/api/password`. GitHub Actions (`.github/workflows/iso.yml`, "Release and ISO") creates the release for every pushed tag `v*` (title = first line of the tag message, text = the rest, in Markdown; a tag with a `-` becomes a pre-release), then builds the ISO and attaches it; a release you create yourself on github.com also gets an ISO. The version in package.json must equal the tag. **Branches:** all work goes to `dev`; `main` only holds official versions. Every push to `dev` or `main` runs `.github/workflows/test.yml` (syntax + tests; on `dev` also a test ISO as a 14-day artifact when the installer changed, or by hand). `dev` never gets releases: test servers use the update channel *Development*. **Releasing a new version:** on `dev` bump the version in package.json, merge `dev` into `main` (fast-forward), push `main`, then `git tag -a vX.Y.Z --cleanup=verbatim -F notes.md` on main and `git push origin vX.Y.Z` (iso.yml refuses tags that aren't on main). Release notes are in English.
- `install.sh` + `deploy/homebaseos.service` + `deploy/homebaseos.env`: installation on a bare Debian 13 (contrib/non-free on, ZFS DKMS, libvirt, Docker from the official source, rsync, optionally `--nvidia`). The app in `/opt/homebaseos`, config in `/etc/homebaseos/homebaseos.env` (only `SESSION_SECRET` is filled in; no `APP_PASSWORD` anymore).
- `test/*.test.js`: tests (`node:test`) for all parsers with sample output of the real tools, and for the checks, the language-independent logic and the ISO.

## Working agreements

- **Everything in the project is English**: code, comments, test names, docs, release notes, commit messages and every text in the interface. Interface text: short, plain sentences, active verbs, error messages that say what is wrong and what you can do.
- **Multilingual (English + Dutch, more later)**: the English text is the key. Put every new text in `app.js` in `t('…')`, with values as `t('Removed: {name}', { name })` (never glue text together), and add the Dutch translation to `public/lang/nl.js` (Flemish: short, plain, "je"). Fixed text in `index.html` (also `placeholder`, `aria-label`, `title`) is translated by `collectStatic()`, but needs a translation too. Server messages are English: the browser translates them with `tr()`, so add a new message to `nl.js` too, as a template if it has values (e.g. `'Port {port} is already used by {app}. Choose another port.'`). Data from the server that is text (warnings, categories, lines of a job) goes through `tr()` when shown. A word with two meanings in another language gets a context: `t('Devices', null, 'backup')` looks up `"backup\u0004Devices"` first (in Dutch *Toestellen* for backups, *Apparaten* for USB/PCI). Never use `t` as the name of a variable or parameter. Apostrophes are fine in keys (escape them in single-quoted strings, also in test names).
- No npm dependencies without asking first. No build step. System packages go through `install.sh`.
- External commands always through `run()` with an argument list, never through a shell. Validate names and paths from the user (see `NAME` and the `ISO_DIR` list in `lib/vms.js`).
- Colours always via the CSS tokens on `:root`. Both themes (light = morning mist, dark = evening) must keep working.
- Everything that comes from the server goes through `esc()` before it goes into `innerHTML`.
- Don't use `confirm()`/`alert()`. Use the own `ask()` dialog in `app.js` (with a third argument you get a checkbox and `ask()` returns `{ checked }`).
- Destructive actions (stop, shut down, delete) always ask for confirmation first.
- Names on disk that existing installs already use stay as they are (e.g. the Dutch folder names of older backup tasks, `/etc/issue.d/homebaseos-wachtwoord.issue`).

## Running and testing

```bash
npm run demo   # demo mode with sample data, http://localhost:8080
npm test       # tests
npm run dev    # on the server itself, settings from .env (see .env.example)
```

There are also configurations in `.vscode/launch.json`.
After a change check at least: `node --check server.js lib/*.js public/*.js`, `npm test`, and click through the demo (apps, app store with installing/removing, storage, backups (tasks, devices, connections), VM page with creating/editing (all tabs)/deleting, console, AI), in English and in Dutch.

## Known uncertainties

- The ISO hasn't really been built or booted yet: the menu changes and md5sum.txt were tested with the files of the real Debian 13.7 netinst, but xorriso (replay), the preseed in the initrd (GNU cpio) and the installation itself not yet. First test: in a VM with UEFI.
- *Update now* was tested with simulated systemctl/curl (success and rollback) and a real download from GitHub, not yet on Debian itself. Releases must contain `lib/update-helper.sh` and have the same version in `package.json` as the tag.
- Two-step verification: the blocking after wrong attempts and the link still to be confirmed are in memory (gone after a restart). Behind a reverse proxy HomeBaseOS sees the proxy's address, not the visitor's (X-Forwarded-For is deliberately not trusted).
- **Not yet tested on a real Debian 13 server.** The parsers are tested with sample output, the commands themselves not yet.
- `virsh domstats` for VMs that are off: vCPU and memory then come from the domain XML (`configInfo`, 60 s cache).
- `virt-install --osinfo linux2022` / `win11`: depends on the osinfo-db in Debian 13.
- `undefine --nvram` leaves the TPM state of Windows VMs (in `/var/lib/libvirt/swtpm`).
- The app store converts templates made for Unraid. All 3956 Docker templates from the feed give valid YAML (tested), but not every app will work without changes (own networks, missing databases, Unraid-specific paths).
- The compose form relies on the JSON shape of `docker compose config` (tested with sample output, not yet with a real compose version). If reading fails (old compose, `${VARIABLES}` in ports), it falls back to the text mode. The same goes for `draft`/`installCompose` (advanced install) and the progress parsing of `--progress plain` (`jobLog`), which are tested with sample output only.
- Moving app data (`lib/migrate.js`) and the default folders are tested with the demo and `replacePath`, not yet with real `rsync`, `zfs create` and `docker compose`. An app without a compose file on the server (`docker run`, Portainer) doesn't move along.
- Without an account anyone who reaches the server can create the first account: do it right after the installation.
- Shared folders are tested up to and including the Samba file and the checks, not yet with a real Samba (`testparm`, `smbpasswd`, `useradd`).
- The terminal on the server is tested up to and including the WebSocket and the security, not yet with util-linux's `script` itself (macOS has a different `script`).
- VM hardware, VM networks and the console are tested with sample XML and a simulated VNC server (noVNC → `lib/websocket.js` → RFB 3.8 with a VNC password), not yet with real libvirt/QEMU. PCI passthrough needs IOMMU (AMD-Vi on in the BIOS); libvirt binds the device to vfio-pci itself (`managed='yes'`). If you pass the GPU through, Ollama doesn't have it while the VM runs.
- Docker networks are tested with sample output of the Docker API, not yet against a real Docker. With macvlan/ipvlan the server itself can't reach the apps (a Linux limitation); Docker refuses a second macvlan on the same card with the same subnet.
- Changing the network is tested with sample files, not yet on a real server. Confirming only works while HomeBaseOS runs (the rollback is a timer in the process).
- The Community Apps feed has no explicit licence. Fine for own use; ask before publishing.
- Backups are tested with a simulated `rclone` and `zfs` (signing in via 127.0.0.1:53682, tasks, progress, restore, encryption), not yet with the real rclone or real cloud services. To check: the JSON log lines with `stats` (`--use-json-log -v --stats`), the output of `rclone authorize` in Debian 13's rclone version, and whether rclone's `/auth` link really redirects. Without a Debian package: install rclone from rclone.org. Passwords in rclone.conf are only "obscured" (reversible), the file is 0600.
- The backup app is tested with the real Kopia (self-built, v0.23.x) on macOS: creating the repository, policy, `server start` with `--random-password --random-server-control-password --no-ui` and our certificate (EC P-256 must have `ec_param_enc:named_curve`, otherwise Go refuses it), `server user add --user-password`, SIGHUP (a new user only works after it), connecting and a backup of a device, `snapshot list --all --json`, and the whole pairing via the HomeBase Backup app against `server.js` (with a simulated `systemctl` and without ZFS). Not yet on Debian itself (systemd unit, `zfs create`, the kopia.io package source). A device's password is briefly on the command line (`--user-password`), the repository password isn't.
- VM snapshots and backups of apps and VMs are tested with sample output and in the demo, not yet with real libvirt/QEMU and Docker. To check on Debian 13: external snapshots with memory for UEFI VMs, `snapshot-revert`/`snapshot-delete` of external snapshots, `virsh backup-begin` (push) and the output of `domjobinfo --bytes`, and restoring an app (tar with `--same-owner`).
- Time Machine via Samba needs `fruit:time machine` (on) and `vfs objects = fruit streams_xattr` (also on); tested up to the Samba file. The quota is a ZFS quota: Time Machine sees it as the size of the disk.
- `smartctl -n standby` gives no temperature for sleeping disks. The interface then shows "Standby".
- ZFS packages (`zfs-dkms`) build a kernel module: after a kernel update DKMS has to build again.
